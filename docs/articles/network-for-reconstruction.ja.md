# 「25が出る画面」から、その動きまで再現するために

原稿状態：公開前ドラフト。2026-10-13作成。実測の対象はNBRET `0fcdfa6` とREA `6.4.0`、2026-10-12のローカル検証環境です。

Webサイトを再現するとき、スクリーンショットは大切な出発点です。文字の位置、余白、色、画像を比較すれば、見た目の違いを確かめられます。しかし、ボタンを押すと何が起きるのか、入力を変えると何が変わるのかを再現するには、画面ができるまでの情報も必要になります。

NBRETが目指すのは、原作を再現するための証拠を集め、その証拠に照らして再実装を確かめることです。既存のCOPYによる画面・DOM・CSSの抽出に、通信や実行されたJavaScriptの観測を加えています。ネットワーク観測は、この取り組みを支える一つの手段です。

## 画面に表示された「25」の手前を見る

画面に「25」と表示されていても、その画像だけでは、固定の数字なのか、計算の結果なのか、保存された値なのかは分かりません。

ここで、ある操作に伴って次の通信が見えたとします。

```text
入力：20 と 5
  ↓
送信本文：{"a":20,"b":5}
  ↓
応答本文：{"result":25}
  ↓
画面に表示された結果：25
```

この情報があれば、再実装するときに扱う入力名と応答の形を、実際に観測した値をもとに決められます。さらに入力を7と3に変え、応答が10になることを確認すれば、「常に25を返す」という仮説を排除できます。

今回のローカル検証では、この二つの入力と応答を実ブラウザで取得しました。通信の呼び出し元JSも記録し、REAが取得したJSとの内容の一致をSHA-256で確認しています。この一致は同じスクリプトのバイト列を取得した根拠であり、原作と再実装の動作が同じである証明ではありません。

## ネットワークの証拠を、再実装にどう使うのか

例えば、商品検索画面を再現する場面を考えます。以下は利用方法を説明する例であり、今回の商品サイトでの実測結果ではありません。

| 観測するもの | 再実装に使える情報 |
| --- | --- |
| 検索語を変えたときの送信 | 検索語やページ番号をどの形式で渡すか |
| 検索結果の応答 | 商品名・価格・件数などのデータ構造 |
| 応答と画面の対応 | どの値を表示し、どの値を整形するか |
| 結果が0件の応答と画面 | 空の状態をどう表示するか |
| 通信失敗時の画面 | 再試行やエラー表示をどう扱うか |

実応答をテスト用の固定データにすれば、再実装した画面に同じデータを与えて比較できます。入力と期待する応答を組にして残せば、動作確認にも使えます。

この「観測した証拠からテストを作り、再実装の差分を確かめる」工程が重要です。現在のNBRETは証拠収集と既存ツールの統合が中心で、任意のサイトについて、この工程全体を自動で完了するものではありません。

## 網羅性は、異なる証拠をつなぐことで高まる

画面、操作、通信、保存状態、JSは、それぞれ違う部分を説明します。

- 画面とDOM・CSSは、何がどこに表示されるかを示します。
- 操作の記録は、どの入力や手順を試したかを示します。
- 通信は、ブラウザとサーバーの間で実際に渡された情報を示します。
- 保存状態の観測は、再訪問や操作履歴による違いを調べる手掛かりになります。
- JSの観測は、ブラウザ内の処理や通信の呼び出し元を調べる手掛かりになります。

NBRETの開発方針は、これらを同じ操作・同じ画面状態に結び付け、原作再現に使える観測範囲を広げることです。現在は、すべてを同一状態で取得できているわけではありません。

また、記録件数が多いことだけでは、網羅性は判断できません。検索成功・0件・失敗、初回訪問・再訪問など、再現したい状態を先に定め、そのうち何を観測できたかを数える必要があります。未観測の状態と取得できなかった情報も残しておくことが、過信を防ぎます。

## 今回確認できたことと、残っている課題

実ブラウザによるローカル検証では、JSONの送受信、入力変更による応答の変化、HTTPキャッシュ利用、呼び出し元JSの記録を確認しました。一方で、次の課題も実測しています。

| 項目 | 現在の状態 |
| --- | --- |
| 別ドメインのAPI | 標準の実行経路では本文が取得対象外になる |
| 遅れて発生する通信 | 原因となった操作ではなく、直近の操作IDが付く場合がある |
| COPYと通信の状態一致 | COPYは新しいブラウザ状態で取得し、操作後の状態を引き継がない |
| REAとの観測時刻 | 現在の統合では、REAは操作終了後の別時間窓で観測する |
| 保存領域とメモリ | storageは件数中心。任意のメモリ内容や全キャッシュの取得は行わない |

改善では、同じページ状態での取得、明示的なAPI取得範囲の指定、操作の観測区間と原因の区別を優先します。これらは今後の改善方針で、対応済みの機能ではありません。

## REAを含め、使える観測手段を組み合わせる

送受信本文の取得はNBRET独自の機能ではありません。今回使ったREA 6.4単体でも、同じ通信の入力20・5と応答25を取得できました。ただし、その実行全体の完全性判定は `incomplete` であり、すべてのイベントを取得できたという結果ではありません。

NBRETは、既存のCOPYとREAを活用しながら、画面の構造と動作の証拠を一つの再現作業で扱う方向へ進めています。REAに対する再現精度や費用面の優位性は、まだ実証していません。

## 原作の再現を、何で確かめるか

通信が見えても、サーバー内部のコードが一意に分かるわけではありません。今回の実験では、内部実装を「足し算」から「値の表引き」に変えても、試した入力に対して同じ通信が成立しました。

そこで、再現の評価では、事前に定めた操作と状態について、原作と再実装の見た目や応答が一致するかを確かめます。観測に使わなかった入力でも試すことで、記録した例だけに合わせた実装になっていないかを調べます。有限のテストで、すべての状態の一致を保証できるわけではありません。

次の評価では、同じ対象・同じAIモデル・同じ予算を使い、COPYのみ、適切に設定したREA、NBRETを比較する予定です。未見入力での再現結果、重要な状態の観測率、作業時間、AI消費量を測ります。今回の実験で確認したのは証拠の取得能力と限界であり、再現精度の向上率やAI消費の削減率ではありません。

NBRETの収集処理自体はLLM APIを呼びません。集めた証拠をAIに分析させたり、コードを生成させたりする工程では別途AIの利用が発生します。

画面から始め、操作と通信を確かめ、必要な状態とコードへ観測を広げる。そして再実装に同じ条件を与えて比較する。ネットワーク観測は、この繰り返しの中で、推測だけに頼る部分を減らすために役立ちます。
