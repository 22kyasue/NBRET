## Decision

**Use ARTEX as the foundation. Understand and configure the existing application before adding software.** Reuse its dashboard, task/chat/workspace, planners/workers, graph, tool/skill/MCP configuration and native traffic/evidence/report lifecycle. Preserve our research corpus, controlled environments, effect checks and canonical client reader around it.

This is Kotaro's product direction, supported by substantial source capabilities. It is not a measured finding that the current installation is effective, configured, contained or even the same build as the saved source. Do not call it a proven service in our setup yet.

## What the research resolved

- ARTEX is a substantial existing application and execution system. It is not merely a scanner wrapper or screenshot. Norma's explicit deny/hard-deny and hook paths are now source-reviewed; older blanket unread/no-check descriptions are superseded.
- Native ARTEX evidence already includes hash/length checking, versioned traffic snapshots and frozen finding/report bindings. Lack of independent effect truth does not imply lack of evidence infrastructure.
- Comparison names hide different systems and versions: maintained versus legacy PentestGPT; BugBase Copilot; three separate PentestAgents; Osgil TARS versus ByteDance; source-assisted Shannon OSS versus commercial black-box claims; renamed Decepticon and current hackingBuddyGPT versus older papers.
- Useful methods recur: explicit hypotheses and disconfirmation, stable task/evidence IDs, prerequisites, typed blocked/partial outcomes, context memory with provenance, fresh controls, restricted report synthesis and directly checked stop outcomes.
- No reviewed comparison establishes a universal independent verifier, all-path scope boundary, general email/self-registration reliability, automatic learning benefit or fair ARTEX-relative superiority. Source mechanisms, documentation, maintainer results and actual runtime observations remain separate.

## Five remaining deployment questions

1. **Existing instance:** Which machine, launch/build, non-mock frontend/backend, image/binary and local modifications produced the intended application? The fuller checkout is documented on KrisPC; saved files here are references, not an installed service.
2. **Topology/state:** Where are data/configuration, database identity, listeners and mounts? Kotaro-PC, KrisPC and container loopbacks differ. Inspect metadata without revealing credentials or dumping environments/databases.
3. **Active profile:** Which provider format/model/base host, tool/agent bindings, skills/MCPs and limits are actually configured? File metadata first. Profile-test/model-discovery/tool-test/MCP-refresh can execute/connect and are not passive inventory.
4. **Enabled execution and stop:** What authority, network/resource policy and supervisor applies to each enabled lane? Which operation stops the intended work? Chat stop explicitly leaves workers/planner running; task pause is not itself observed quiescence.
5. **Native export:** What already saved neutral artifact exposes actual IDs, versions, raw-body hashes/lengths, completeness, principals and build context? Inspect it before deciding any translation code is required.

These are the immediate inputs for using ARTEX. Missing original ancestry/Norma license-at-pin remain provenance matters for later copying/distribution; they do not justify an alternative foundation or prevent read-only understanding. Open questions about unused rival integrations need not delay this inventory.

## Path from inventory to a useful baseline

After actual configuration and enabled-lane authority are established, the smallest separately admitted progression is:

1. Inert model/stub compatibility observation, without target execution.
2. Existing owned disposable control through the selected ARTEX workflow, with explicit input/access and aggregate budgets.
3. Freeze original native actions/results before reviewer controls or replay. Keep guided plumbing separate from ARTEX-selected investigation and preserve misses/failures.
4. Review policy, principal, object/build and actual consequence with appropriate legitimate/negative controls. A native confirmed label or schema-valid proof paragraph is a claim, not independent authority.
5. Manually map actual reviewed results to the existing canonical reader; automate only if a concrete repeated mapping gap appears.
6. Use the named task/work stop and observe relevant requests/processes/listeners/queues/supervisor settlement. Preserve unverified stop and partial work as non-pass states.

This progression is a decision sequence, not an instruction to resume stopped research, run providers/targets, expose a fixture publicly or start an autonomous production-site assessment. A no-finding result is valid; it is not a clean-security guarantee. Same-host guided corroboration is useful without claiming protected custody or hidden scoring.
