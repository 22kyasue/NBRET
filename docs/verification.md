# 検証記録 — 2026-10-12

Windows / Node.js 24.14.0 / Playwright 1.64.0 / REA 6.4.0。ブラウザはheadless実Chrome/Chromiumを使用。

`npm test` の3ケースで以下を確認しました。

1. 通信取得：POSTの入力20/5とJSON応答25、requestId・操作ID・initiator、キャッシュ再利用、DOM寸法、storage件数、機密キーのマスク、明示指定したJS保存。
2. 上限：個別本文、2レコードの件数上限、4,096バイトの総保存上限、省略カウンタ。レコード/素材の無制限保存を防ぐ。
3. 統合：公式REA CLIの実接続、COPYの1440/390 DOM・CSS・PNG出力、20/5→25と7/3→10の入力・応答本文照合、通信initiatorのJSとREAが取得したJSのSHA-256一致。
4. 失敗処理：不正なfill先で実際に失敗させても入力値をsummaryへ保存しない。既存runへの再実行を拒否。

試験には同梱のローカルHTTP fixtureだけを使用。REAのcode0やHTTP200だけで成功とはせず、具体的な入力・本文・ソース一致をassertしています。

既存COPYの抽出部分は実行確認済みです。収録したmirror全ページ巡回、全比較ツール、任意の実サイトの複製品質は今回一括検証していません。計算サーバーの元コードを復元したという結果ではありません。

レビューで指摘された失敗メッセージからの入力漏れと保存資源の上限不足を修正しました。REA/COPYには別の取得範囲があり、REAのpolicy_filteredやnetworkのdroppedを「完全取得」と読み替えないでください。
