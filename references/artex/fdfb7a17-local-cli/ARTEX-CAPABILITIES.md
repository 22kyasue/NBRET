# ARTEX and local-cli-bridge: source-grounded capability report

Prepared for Kotaro, 2026-10-21 (JST). Investigation only.

## Executive answer

ARTEX is an LLM-controlled execution and investigation platform: it turns task goals into a shared exploration graph, schedules a planner and parallel workers, lets agents run real shell/file/web/custom/MCP tools, stores assets and findings, and produces reports and evidence links. It is not a fixed scanner with a guaranteed list of detectable vulnerabilities. Its practical reach depends on the chosen model, installed programs, network access, enabled tools, database bindings and interception rules.

The local addition `tools/local-cli-bridge` is a text/tool-decision adapter. It exposes a small OpenAI Chat Completions-compatible HTTP interface and launches logged-in Codex or Claude CLI processes to generate decisions. Returned ARTEX tool calls are inert JSON until ARTEX executes them. The bridge does not itself implement scans, vulnerability verification, an ARTEX scheduler, or an ARTEX execution sandbox.

**Important:** CLI read-only/tool restrictions do not make ARTEX read-only. ARTEX workers explicitly use the SDK's bypass permission mode and real execution tools; their separate interception hooks determine whether a call is allowed, denied, or sent for human approval. [agent/worker.go](sources/agent/worker.go), lines 429–473; [guard/guard.go](sources/guard/guard.go), lines 81–132.

### Tool wiring details that affect “exactly what can run”

The final chain is role base tools → skill/MCP/host augmentation → DB tool resolution → finding-workflow adjustments → name aliases and panic wrapper. See `agent/assembly.go:26–72`. In `server/assembly.go:239–323`, DB-known tools must be enabled and bound to that agent, while tools with no matching DB row pass through. A failed tools-table read returns the original tool list (`241–244`), so this is not fail-closed authorization. SDK general tools are intentionally not seeded as editable domain rows (`agent/toolcatalog.go:31–34`).

Concrete role inventories:

- Worker domain base: `list_findings`, `report_finding`, `record_fact`, `insert_assets`, `list_assets`, `search_all_worker_traces`, `get_worker_trace`, `node_detail` (`agent/tools_insert.go:644–660`).
- Planner domain base: graph/finding/fact/node/digest reads; worker output/trace/search; goals; `add_intent`, `prove_goal`, `goal_met` (normally removed by default binding), `kill_work`, `steer_work`, `report_finding`, company/assets/scope/untested-asset tools (`agent/tools.go:2032–2053`).
- Mainagent adds human-driven hints, intents, steering, goals/constraints and asset/scope writes (`agent/tools_insert.go:664–681`).
- Host traffic tools: `traffic_search`, `traffic_get`, `traffic_blob`; absent when capture is off (`traffic/traffic.go:2000–2123`; `server/manager.go:740–748`).
- Cross-task registry: `list_tasks`, `list_llm_profiles`, `spawn_task`, `pause_task`, `get_task_graph`, `list_task_findings`, `add_task_hint`, task trace/list/search/detail, `update_finding_report`, `get_finding_traffic`, `bind_finding_traffic` (`server/orchestration.go:65–81`, handlers beginning at 176).
- Custom `shell` kind only appends installation hints to Bash; it does not install a binary or implement a callable handler (`server/assembly.go:290–305`). Custom `command` invokes the SDK Bash handler; `script` invokes Python; `http` makes an HTTP request (`server/customtool.go:345–458`).

**Important:** The actual active registry cannot be reconstructed from source alone because tools, agent bindings, MCPs, skills and interception rules are stored/configured at runtime. The matrix is a source capability inventory, not a live configuration certification.

## Bridge request/response flow

All paths in this section are under `tools/local-cli-bridge/` (copied under the same relative path in `sources/`).

1. **Startup:** `start.ps1:3–24` creates a bridge runtime directory and, if absent, a 32-byte random bearer token encoded as Base64. It checks authenticated health, refuses an occupied port, and launches Node hidden with stdout/stderr logs and a PID file. It does not log into either provider. `main.mjs:5–19` parses only token-file/port/host arguments, restricts its bind host to loopback, validates the port, reads the separate bridge token or token environment variable, and builds the server/runner.
2. **HTTP admission:** `server.mjs:50–70` requires a token of at least 32 characters, rejects requests carrying Origin or Sec-Fetch-Site, verifies exact Bearer authorization with timing-safe comparison, and serves only authenticated `/health`, `/v1/models` and `POST /v1/chat/completions`. JSON requests are limited to 1 MiB. `/health` reports the HTTP bridge as healthy; it does not test provider login or inference.
3. **Validation and translation into a prompt:** `protocol.mjs:58–83` accepts exactly `local-codex` or `local-claude`; nonempty message arrays with system/developer/user/assistant/tool roles; text content (including narrowly allowed omitted/null content for tool history); up to 128 uniquely named function definitions; n=1; tool-choice auto/none/required/named. It serializes the transcript and tool definitions into a single JSON-bearing text prompt. Roles/IDs are preserved as data, not sent as separate native CLI conversation roles.
4. **Queue:** `server.mjs:5–22,54,60–73` grants one execution slot per provider with at most four waiting requests per provider. Codex and Claude may run concurrently with each other, but same-provider calls serialize. Queue overflow returns 429. ARTEX has its own 30-second connection-test deadline (`agent/provider.go:457–462`), which can fail before a cold CLI finishes. The 120-second server timer begins before request-body parsing and queue admission, so waiting consumes the deadline.
5. **CLI process:** `runner.mjs:28–112` starts a fresh child with shell=false, hidden Windows window and stdin/stdout/stderr pipes. Prompt goes to stdin. Codex receives an isolated temporary CWD and a schema file, later removed; Claude uses the supplied CWD (default process CWD). The two external aliases choose providers and normally leave the underlying model to CLI defaults; the HTTP validator does not accept arbitrary model names, even though the runner helper can accept an explicit model internally.
6. **CLI result:** Codex JSONL must contain a completed agent message and usage; disallowed native-tool item types cause rejection. Claude must return a success envelope with structured_output. Usage is normalized to prompt/completion/total tokens (`runner.mjs:113–148`).
7. **Decision validation:** `protocol.mjs:85–99` requires `{content, tool_calls}`; an empty answer with no calls is invalid. Every proposed call must name a submitted tool, contain an argument string that parses to an object, satisfy the supported argument schema and obey tool_choice/parallel constraints. It does not execute the function.
8. **Response:** `server.mjs:75–89` assigns new call IDs and returns an OpenAI-shaped assistant message with finish_reason `tool_calls` or `stop`. ARTEX's agent loop is responsible for executing the selected registered tools and sending resulting history on the next model request. The bridge has no persistent multi-turn conversation store; history must be supplied again.

### Security findings and operational limits

- **Important:** Codex native-tool-event rejection is post-execution-output validation. The runner buffers the process output and only checks events after the process closes; it cannot undo any native side effect that happened before rejection (`runner.mjs:70–120`). The read-only/feature flags remain the preventative controls, contingent on CLI enforcement.
- **Important:** This is local transport, not local inference. Prompts contain the supplied ARTEX history and tool results and are handed to authenticated provider CLIs. The bridge does not redact secrets from that content. Provider handling of that content is outside this source review (`protocol.mjs:81–82`; `runner.mjs:111`).
- **Important:** Loopback binding and the bearer token restrict bridge access, but are not per-task permissions. The code does not set a token-file ACL, implement TLS, restrict tool names to an ARTEX allowlist independent of the incoming request, or check a caller's target authorization (`start.ps1:6–13`; `main.mjs:11–19`; `server.mjs:24–27,64–78`). No token or environment value is included in this delivery.
- **FYI:** The README recommends a Docker host URL while the server binds loopback (`README.md:16,25–26`; `main.mjs:11–12`). Whether the particular Docker/Windows networking stack can reach that listener was not tested; do not infer connectivity from the configuration example alone.
- **FYI:** The bridge has no code for selecting a paid API fallback. Codex explicitly forces ChatGPT login, but the absence of fallback code is not independent proof of the installed CLI's account/billing state. Neither CLI version nor authentication state was queried.
