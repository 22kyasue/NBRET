## Scope and result vocabulary

The outcome is an openly guided, disposable local URL-to-report rehearsal of all eight stages. Only the new typed transport and owned numeric-loopback target/mailbox are admitted. No providers, external inbox, scanners, browsers, arbitrary helpers, production access or hidden benchmark. An unrestricted coding session is outside the transport's enforcement boundary.

Use `passed` only for a specific observed acceptance condition; preserve `not-attempted`, `blocked`, `failed`, `inconclusive` and `interrupted` with reasons and evidence links. The evaluator's `demonstrated`, `not-demonstrated` and `inconclusive` describe the selected ownership-read effect, not overall application security. A denied or empty response is not a clean bill of health. A guided successful disclosure is not an independently admitted verified finding.

## Evidence ledger required for an acceptance decision

For each secure/control run retain a run ID, start/end times, actual command, source/config hashes, build ID, generation, all eight stage dispositions, safe transport receipts and evidence IDs, evaluator output, reviewer objections, report artifacts and cleanup observations. Record attempted/sent/completed/errors/denied/active/stopped counts, caps and interrupted/skipped actions. Preserve earlier failures when a later attempt succeeds.

Build/generation annotations come from the local collector/operator; caller-written labels are not authenticated provenance. Evidence selection must reject mixed generations as well as mixed builds. A digest of raw response bytes supports integrity comparison; it neither makes the redacted body complete nor proves the response's identity by itself. Review every exported body, URL, header and exception for credentials, mailbox/verification tokens and synthetic secrets. A digest without retained raw bytes is not a recoverable raw archive.

## Readiness questions and potential overclaims

1. The contract specifies stages but not a stage-state schema or persistent acceptance ledger. Orchestration must expose evidence-backed stage dispositions; a narrative saying all eight completed is insufficient.
2. The evaluator contract initially names `buildId` and receipt generation annotations. Require a consistent nonempty generation across all inputs, and preserve request identity separately from corroborated `/api/me` identity. Neither is external custody.
3. Independent challenge needs a named author and concrete adversarial inputs/results. Do not promote local evaluator output into independently verified findings.
4. Listener/connection closure, zero transport activity and reset are separate observations. A fresh build ID alone does not prove data reset; source-stable runs should have separate generations.
5. Verification is an intentional state-changing GET in this disposable app. Method labels do not imply read-only behavior; this route must be explicitly admitted.
6. The HTTP transport bounds HTTP requests. Confirm whether SMTP delivery has its own address, message-size, connection and timeout bounds; do not claim the HTTP request cap bounds every internal operation. Require teardown on partial target/mail startup and exceptions as well as happy-path completion.
7. A secure control that denies this one selected read does not establish coverage of other routes/classes. A deliberate ownership-gap run demonstrates a guided effect only. Neither proves autonomous discovery, service readiness, a real changed-build repair or held-out scoring.
