# ARTEX at the core: capability and integration map

Thistle · 2026-10-21 · source review for Cass

ARTEX already supplies an investigation application, not merely a model adapter. Its pinned frontend connects task control, live sessions, traffic, findings, approvals and reporting to a sizeable backend API. We should evaluate those paths before constructing another operator application. The useful NBRET contribution is research-informed investigation methods, bounded observation adapters, independently established effects and a trustworthy client report.

This is **source-trace evidence**, not an executed compatibility, containment or detection result. Nothing here authorizes launching ARTEX, calling a provider, installing dependencies or contacting a target.

### What the UI cannot establish

The API client has a mock branch as well as real HTTP requests, bearer authentication and 401 handling ([web/src/lib/api.ts:126–159](https://github.com/jiwoochris/artex-global/blob/fdfb7a17b7da5e2de716c0e98475ec77a41c64c6/web/src/lib/api.ts#L126-L159)). A populated dashboard alone therefore cannot prove a live backend. SSE authentication appends the token to the stream URL ([web/src/lib/api.ts:201–209](https://github.com/jiwoochris/artex-global/blob/fdfb7a17b7da5e2de716c0e98475ec77a41c64c6/web/src/lib/api.ts#L201-L209)); evaluate deployment/proxy logging and access controls without reproducing tokens in reports.

The actual rule database, enabled tools, skill contents, MCP endpoints, model profiles, credentials and backend deployment determine the active system. This review does not certify their configuration. Likewise, a UI route's presence does not prove backend authorization for every operation. Error, reconnect, retention and secret-redaction questions remain acceptance questions, not newly discovered runtime defects.

## Exact extension seams and their boundaries

**1. Research-informed methods through agent prompts and skills.** Use existing prompt versions, preview and skill management rather than inventing another method store. Admit compact, source-backed investigation recipes: observed preconditions, permitted action classes, discriminating evidence, negative controls, stopping conditions and known failure modes. Link recipes to research IDs and opened studies. Never copy hidden scorer answers into skills, search or investigator workspace.

**2. Approved observation through an MCP or deliberately bound tool.** `server/assembly.go:1–165` loads agent-visible extensions and skill-associated MCP tools; `agent/assembly.go:1–94` composes tools and applies final resolution. That is the concrete candidate seam for the existing computeruse harness, capture/session collectors and dedicated inbox reader. Return bounded observations and artifact references, not arbitrary host authority. First design schemas for route/form/session observations, authorized account state and capture omissions. Browser/form/MFA/multistep coverage remains unproven until the actual installed toolset is inspected and exercised on owned controls.

**3. Evidence export adjacent to finding traffic, not a second finding engine.** `server/finding_traffic.go:94–105` defines binding/detail/body routes; frontend API `614–680` exposes them. Use these identifiers to link captured requests and response bodies to an NBRET journal/casebook record. Retain original task/finding/binding/version identifiers and acquisition provenance. Add explicit engagement, principal, action, environment/build/generation and artifact hashes where the source payload supports them; mark unavailable fields unknown. Do not infer all of those identities from a task name or timestamp.

**4. Independent effect verification beside execution.** Existing retest endpoints are a launch mechanism; the verifier must independently compare allowed controls with the claimed unauthorized effect and preserve denied/error/inconclusive outcomes. For the owned local rehearsal, retain the already implemented identity-bound effect checker and actual HTTP/SMTP evidence. Do not expose hidden source/scorer/control labels to the investigator through the MCP, workspace or shared chat. Feed admitted results into the canonical `src/practice/reader-report.mjs`, `reader-model.mjs`, `reader-ui.js` and `reader-ui.css` in the preserved track. Export/admission mapping is work to implement and test, not an existing ARTEX integration.

**5. Deterministic admission outside model judgment.** `server/assembly.go:239–323` filters known disabled/unbound tools, but a tool-table read failure returns the input list and unknown tool names pass through. `guard/guard.go:81–132` allows absent/disabled interception and unmatched calls with no active judge. Configured deny/ask paths do block; this is useful functionality with conditional coverage. `enrich/enrich.go:180–249` performs engine-side DNS/HTTP enrichment outside the model's selected tool call. Thus a prompt, bridge read-only flag or UI rule is insufficient as the whole boundary. Cover SDK tools, custom processes, MCPs and enrichment with separately validated destination/resource controls and cancellation. No claim of an observed escape is made here.

The local bridge supplies model decisions; its CLI restrictions do not constrain ARTEX's subsequent dispatch. This is the existing source-supported research entry `agent-runtime.artex-cli-bridge-not-engine-permission-boundary`, opened at `docs/research/security-landscape/art-external-platforms-20261020.md:39–49`. `safety.capability-gate-outside-model` is only component-lab evidence for selected decisions; it is not whole-host isolation. `ai-evaluation.audit-evaluator-before-tester` is a proposed evaluation framework, not a measured ARTEX result. These distinctions prevent accumulated research from becoming overstated certification.

## Smallest meaningful evaluation slice

Evaluate one owned, explicitly guided URL-first investigation through ARTEX's existing task/session interface. The investigator receives an ordinary URL, readable dedicated inbox capability and admitted observations, rather than a prescribed sequence or source answers. It must choose its next step from observations, register/authenticate if needed, form one testable access-control hypothesis, collect a negative control and preserve the result even when inconclusive. A familiar local target is guided learning, not held-out performance.

Before execution, establish the actual running version, non-mock backend, admitted tools and outer boundary. During evaluation use ARTEX sessions/traffic/approvals as the operator view; cross-check them against independently recorded owned-target effects. Deliberately test one harmless denied action and one stop with an in-flight owned operation. Completion requires observed refusal/quiescence and accounted artifacts, not merely a UI label. Keep the canonical report as the final client artifact. This is an evaluation proposal; no such ARTEX run occurred in this task.

UI validation should answer:
- Can an operator identify the active task, account, target, build and pending decision without reading raw transcripts?
- Do task switches, SSE failure/reconnect and page refresh preserve sequence and expose gaps or stale data?
- Are denied/error/timeout outcomes distinct from successful actions and verified effects?
- Does pause/stop become quiescent across workers, tool descendants, MCP and enrichment, with no later activity?
- Are credentials/bodies protected in chat, records, traffic, SSE URLs, exports and workspace downloads?
- Can a reviewer follow each report claim to the exact evidence version, control and retest history?

## Three avoidable rebuilds and three actual gaps

**Avoidable rebuilds:** (1) another dashboard/live task monitor; (2) another planner/worker/chat lifecycle framework; (3) another management application for tools, MCP, skills, workspace and model profiles. ARTEX has concrete source for these. Reuse remains conditional on runtime acceptance, not automatic adoption.

**Actual gaps in our integration/evidence today:** (1) validated execution containment and end-to-end stop behavior for the actual ARTEX configuration; (2) a versioned export/admission adapter joining ARTEX evidence to independent identity/build-bound effect and retest records and the canonical reader; (3) demonstrated observation-driven URL-first signup/authentication/multistep investigation using approved harness/inbox capabilities and admitted research methods. Existing UI, upstream declarations and a fixed rehearsal do not close those gaps.
