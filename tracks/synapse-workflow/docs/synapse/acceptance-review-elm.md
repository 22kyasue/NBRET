# Synapse local foundation acceptance review

Elm, 2026-10-18. Requested by Skye; architecture and integration remain Skye's responsibility. This is an implementation acceptance proposal grounded in existing research, not new research or a measured result. Source inspection only; no tests, experiments, demos, inference, target requests, installs or deployments were performed.

The immediate increment is an offline journal/store with deterministic investigation state, review records and reports. Existing interactive coding-agent sessions can author records. It has no target executor or model-provider startup. Passing this increment establishes that the workflow preserves and qualifies records. Discovery effectiveness requires a separate evaluation.

## Ranked blockers and decisions

1. **Confirmation must require evidence beyond a status field.** A candidate author, reviewer string or matching hash cannot establish an effect or reviewer independence. Store the claimed effect, evidence references, producer, identity/environment binding, completeness, review rationale, objections and actual verification provenance separately. An offline record can say that verification was reported, with its basis; it cannot manufacture independently observed verification. Missing or inconsistent required evidence blocks promotion. Kotaro verification remains a separate event.
2. **Define journal commit and recovery semantics before calling the workflow resumable.** Require ordered revisions, atomic conflict detection and immutable committed events. A single writer with an exclusive lock and explicit stale-lock recovery is sufficient for v1; a worker fleet is unnecessary. Reopening a journal reconstructs pending work without executing it. No automatic replay of external effects is supported. A stopped investigation stays stopped after reopen.
3. **Record the actual separation boundary.** Sessions and directories under the same unrestricted OS user provide procedural separation only. They cannot establish hidden-key confidentiality or prevent journal rewriting by that user. Blind evaluation admission needs a separately protected preparation/key location and an access/context inventory. Without that boundary, label results assisted or potentially contaminated, even if the workflow tests pass.
4. **Freeze evaluator and baseline before effectiveness claims.** Agree a realistic manual baseline operator, access, budget, assistance policy, eligibility and adjudication protocol. The local foundation can be accepted while those decisions remain pending, but no comparative quality claim follows.
5. **Keep the legacy evidence path outside the accepted identity-sensitive route.** `src/assessment/core.mjs` has exact actor/session/configuration binding checks; `src/checks.mjs:82` still selects offline evidence by method, URL and body. Choose the assessment contract as a reuse candidate, or implement an equivalent explicitly reviewed binding. Do not silently import the legacy matching semantics.

## Required offline workflow checks

These are proposed acceptance checks, to implement in a dedicated offline suite after task ownership. Every check must retain expected and actual outcomes, reached assertion counts and fixture identities. No HTTP servers, browser sessions, scanner processes or inference are needed.

| ID | Concrete check | Pass condition |
| --- | --- | --- |
| L01 | Create an investigation with scope/authorization reference, mode, environment revision, identities, budget, exclusions and policy revision. Reopen it. | Required fields and revision survive unchanged; missing authorization is explicit; recording a URL or approval reference never initiates execution. |
| L02 | Append hypothesis, observation, candidate, review, pending-action and stop records, then render all three output categories. | Each disposition cites its basis; verified findings, promising issues needing action and unconfirmed leads remain distinct; unknowns and dissent survive rendering. Zero findings is a valid terminal outcome. |
| L03 | Change principal, tenant, role, session, environment revision, oracle or policy in an otherwise identical evidence reference; add a duplicate or remove an artifact. | Each mismatch/ambiguity becomes unavailable or inconclusive; none can confirm a finding or close a repair. Missing evidence takes precedence over partial successful checks. |
| L04 | Alter one committed byte, remove/reorder a committed event, replace a referenced artifact and truncate the last write. | Integrity/revision inconsistency is detected and review/promotion is blocked. Recovery exposes the last intact committed prefix and the damaged tail without silently rewriting history. Whole-store replacement by its owner remains outside hash-chain protection. |
| L05 | Inject a failure before and after the commit boundary; reopen each result. | Each event appears once or is visibly uncommitted. Acknowledged durable events survive process reopen; projections rebuild from committed events. Document durability limits under power loss and filesystem behavior. |
| L06 | Two writers attempt the same expected revision; retry an identical operation ID, then reuse it with a different payload. | One writer commits; the other gets a conflict with no lost event. An identical retry is idempotent; conflicting payload reuse is rejected. Resume never repeats a completed operation merely because the caller missed its acknowledgement. |
| L07 | Stop, reopen, request a normal append and attempt a resume. Repeat with changed scope/policy or expired authority. | Stop reason and pending work survive. Passive evidence/review records may continue if policy permits; work-state advancement requires explicit resume and current authorization. Changed authority creates a new linked revision; no quiet expansion occurs. |
| L08 | Attempt self-review, a review with no rationale, missing effect evidence, a broken positive control and a relabeled automated decision presented as human verification. | Invalid transitions reject. Self-review fails by recorded identity; independent/human provenance remains declared unless separately evidenced. Distinct actor strings alone never earn a technical independence claim. |
| L09 | Revise a finding, reject it, reopen it with new evidence, export and reload it. | Original interpretation, review objections, rejection reasons, evidence IDs, redaction/transformation history and supersession links survive. Report generation does not mutate source records. |
| L10 | Retest with synthetic recorded outcomes: original case passes, control fails; oracle changes; evidence missing; original and selected neighbouring cases plus legitimate controls pass. | First three remain inconclusive. The last supports only repair verified for the listed cases/revision. No disappearance or missing case becomes a fix. |
| L11 | Add synthetic credential canaries to allowed structured fields, free text and export metadata. Attempt invalid input, unknown operation, path traversal and output overwrite. | Secrets are rejected or redacted according to an explicit field policy, without becoming an oracle success. Unsafe paths/operations reject and old artifacts survive. Export omissions are disclosed. No claim of universal secret detection follows. |
| L12 | Evaluate a scorer using intended success, wrong identity/object, stale success-shaped state, partial error, extra effects, missing evidence and a deliberately failing assertion. | All required constraints discriminate as specified; intended assertion paths demonstrably execute. Counts distinguish selected, skipped, executed, incomplete and adjudicated records. Store completion never substitutes for an effect verdict. |

Acceptance requires all applicable L01–L12 checks with evidence, documented unsupported behavior and no concealed failures. Exact file/event schemas belong in Skye's architecture contract. If an operation such as active resume or retest is deferred, its command must explicitly reject unsupported use; a metadata-only record cannot be advertised as the deferred capability working.

## Existing tests worth reusing

Read `test/assessment.test.mjs`, `src/assessment/{core,transport,cli,matrix}.mjs`, `src/http.mjs` and the legacy matcher. Existing tests were inspected, not rerun. Most assessment tests start loopback servers, so do not invoke the full suite for this offline increment.

Useful patterns to port into pure recorded-data tests:

- Exact actor/session/configuration matching, duplicate rejection and entry-byte integrity checks in the offline-reuse test. Its HTTP fixture is setup scaffolding, not necessary to test those predicates.
- Broken positive controls blocking confirmation; all-denied outcomes preventing repair closure; changed retest oracles becoming inconclusive.
- CLI retest rejecting results changed independently of retained evidence. Keep the evidence-to-report invariant even if the new journal uses a different schema.
- Matrix generation resetting authorization to draft without mutating its input; unknown flags and overwrite refusal.
- Incomplete evidence and budget omissions remaining incomplete rather than passing.

Limits visible in current code: `reviewFindings` validates nonempty reviewer/rationale fields and positive controls, but does not authenticate a reviewer, prove different authorship or establish fresh reproduction. `caseBinding` binds operator-declared identity labels, not an authenticated session observation. `runAssessment` writes checkpoints but the assessment CLI has no resume command. `executeCase` checks abort before a request; `requestBounded` has no abort-signal input, so an in-flight request continues to its own response/deadline. The pre-execution cancellation test does not establish active cancellation or target-side quiescence. These are source findings about the inspected path, not runtime measurements. Keep executor work outside this increment.

## Effectiveness evaluation admission

Use two visibly different modes, as discovery-decisions.md now requires. In a blind scored run, freeze target and scorer versions before access, keep the answer key inaccessible to investigators/reviewers, and prohibit investigative hints before submissions freeze. Kotaro does not open the key before that freeze. Record any incidental disclosure and affected cases. Safety or scope clarification is always allowed but logged; assistance that changes investigation knowledge contaminates that unit for independent discovery scoring. Frozen findings are independently adjudicated, including unexpected findings. Once answers are exposed, later work on that target is familiar-target practice.

In guided learning, Kotaro may steer and ask freely. Log hints, supplied evidence and interventions with timestamps. Evaluate explanation quality and reproduction usability, but do not pool assisted discovery with blind results. Teaching in blind mode describes observed evidence and limits only. A short teach-back or independent reproduction can measure whether the explanation helped; no passing teaching score is currently established by research.

For a manual baseline, nominate a competent human operator before the run. Use equivalent scope, credentials, tooling allowance, access-ready start, time/resource budget and deliverables; record expertise and familiarity. Freeze outputs before the operator sees the answer key or the other arm's results. Use protected unseen comparable variants and counterbalanced assignment where feasible; the same person repeating the same revealed task is a practice comparison. If no competent unexposed operator is available, report descriptive workflow measurements and defer the improvement claim. Do not replace an expert baseline with another model and call it manual.

Before admitting scored tasks, independently verify scorer feasibility and the L12 negative controls. Freeze the eligibility rule and adjudication procedure; keep infrastructure errors, unsupported work, unscored runs, timeouts and attempted failures in the run ledger. A newly discovered scorer defect quarantines the affected comparison; version the repair and re-adjudicate every affected arm from retained evidence. Do not quietly discard inconvenient runs.

## Rejected-candidate sample audit

Preserve every proposed candidate before filtering, including rejected and incomplete candidates, with reason, evidence references, filter version and cost. Missing evidence is its own disposition. Define duplicates by a documented root-cause rule; keep their original IDs linked.

Proposed initial operating default, not a research-derived optimum: audit all rejects when there are at most 20. Above 20, randomly select 20 across rejection-reason strata with at least one from each nonempty stratum; if there are more than 20 strata increase the sample to cover them. Also audit all high-consequence or provenance-related rejects. Record the frozen population, sampling seed, inclusion probabilities and which cases were mandatory rather than random. The auditor sees the candidate evidence before the filter rationale to reduce anchoring, and records an independent disposition first.

Report missed-valid candidates / adjudicated sampled rejects, inconclusive counts and per-stratum results. Mandatory reviews are reported separately. Any population estimate must account for unequal inclusion probabilities; do not extrapolate a convenience sample. This measures filter rejection error among submitted candidates, not discovery recall over all possible issues. Escalate a material missed-valid reject to review of its reason stratum and affected prior decisions. If budget cannot support the promised audit, mark the evaluation incomplete or publish that blind spot explicitly; never assume unaudited rejects are correct.

## Separation and provenance limits

Separate preparation, investigation, review and adjudication contexts. Preparation materials/key stay outside investigation roots, shared boards, handoffs, search indexes and model context. Handoff packages contain only allowed evidence and verification instructions, with read-only permissions where enforceable. Reviewer records initial observations before seeing the author's verdict where practical. Record package contents, access grants and known prior exposure.

On this PC, unrestricted same-account sessions share filesystem and tool authority. Different directories, session names or a promise not to look are procedural controls. Technical key confidentiality requires a separately controlled OS account, machine or equivalent boundary with restricted mounts and tools; this review does not authorize setting one up. Even a separate session may share model training or correlated reasoning. Report whether confirmation was fresh effect reproduction, independent artifact inspection or simply agreement. A signature authenticates a producer only under a separately established key trust model; a hash alone proves neither origin nor truth.

## Measurement, iteration and stop rules

Freeze a run manifest: mode, target/build/policy/scorer/tool versions, initial access/knowledge, eligible cases, resource ceilings, attempted-run count, stopping rule and assistance policy. Record stage times for preparation, exploration, filtering, review, Kotaro reproduction, report editing and retest; include failures and setup/maintenance effort. Existing subscriptions may have zero marginal API charge while still consuming time/resources; label unknown cost rather than inventing savings.

Report independently adjudicated unique findings, false claims surviving review, inconclusive claims, eligible planted-case recall only where a complete key exists, clean-case behavior, reproduction success, impact overstatement/understatement and total labor to verified result. Preserve exact denominators and per-case outcomes. A real application without a complete answer key cannot establish recall. Repeated prompts on the same target are correlated units. Choose repetition count and uncertainty analysis before comparative runs; the research does not establish a universally sufficient sample size or quality threshold.

Optimize one bottleneck at a time using development cases, then test the frozen change on unseen evaluations. Prefer fewer unsupported claims and lower total review burden at comparable verified coverage over raw candidate volume. A faster record append is a storage result; it is not faster independent verification. For the offline store, use deterministic synthetic journals at declared sizes, measure rebuild/append/report time and memory on this PC, and set performance budgets from observed needs. No production SLA or benchmark claim is established now.

Immediate stop conditions for future work: authorization/scope expiry or revocation, hard time/resource ceiling, unexpected external access or side effect, uncontrolled credential disclosure, provenance corruption or loss of required controls. Freeze evidence and record unresolved effects; do not delete the journal. Blind-key leakage stops the independent-scoring claim for affected units, while separately authorized guided learning may continue after explicit mode change.

Proposed diminishing-returns default: review two consecutive fixed-budget windows with no new independently supported hypothesis, useful surface evidence or reduction in material uncertainty. Stop only after recording the remaining permitted alternatives and why they are exhausted, blocked or lower value than the remaining budget permits. Window size and hard ceilings must be configured before execution; this heuristic is an operational proposal, not a validated optimum. Do not require a serious finding to finish.

The offline foundation's stop means no further active work-state advancement, preserved committed records and explicit resumption requirements. It must not claim to stop external work it cannot control. Any later executor needs separate cancellation, authority revocation and observable quiescence/reconciliation checks before claiming an effective stop.

## Stage 1 implementation and reciprocal review receipt

After this proposal, Skye assigned Elm `src/investigation/records.mjs` and `test/investigation-records.test.mjs`. The implementation exports `initialState`, `applyEvent`, `replay` and `summarize`, with no imports or target execution. Six focused pure tests pass: deterministic immutable replay/provenance; manifest boundaries; support/self-review/evidence checks; later review/negative verification handling; request/stop/reopen behavior; and strict plain-JSON/input rejection. Command: `node --test test/investigation-records.test.mjs` (6 passed, 0 failed, 0 skipped). This is lifecycle evidence only. Bryn's independent source review found no blocking lifecycle issue and requested parity with the store's rejection of negative zero; that rejection and its regression case are included.

The current summary supplies full lead-object arrays `reviewSupported`, `needsAction`, `unconfirmed`, `rejected`, plus `pendingRequests`, `progress`, `stopped`, `limitations`; it additionally supplies `status`, `counts`, ID `categories` and total `minutes`. Review and verification histories are retained. Current status uses the latest review, while a latest negative/inconclusive owner verification blocks positive presentation until a later reproduced declaration. None of these records earns an independently verified effect label. Actor/producer differences are declared IDs only.

Implementation narrows the proposed L01–L12 contract: scope grants, effect validation, actual artifact loading, automatic secret sanitization, active execution/resume and real repair verification remain deferred. Unknown event fields/operations reject. Target metadata has no credentials/query/fragment. Stop is terminal for fresh lead/evidence/request intake; passive review, owner verification, resolution and progress may still be recorded. Reopening is reconstruction, not an authorization renewal or restart. This foundation must not be described as passing every full-v1 acceptance check above.

Reciprocal source inspection of Bryn's journal found no blocking issue in the cooperative local-operator design. CAS and semantic validation run under the same exclusive lock; publication uses synced temporary bytes and atomic no-overwrite hard links; committed chain gaps/changed bytes and interrupted pending files fail closed. Exact duplicate retry requires current revision/head, preventing a stale caller from bypassing CAS. An interrupted lock or pending entry requires explicit operator inspection; no automatic recovery is implemented. Crucially, deleting a complete suffix cannot be detected from the shortened store alone: a separately retained expected revision/head is needed. L04 must therefore distinguish interior corruption from suffix rollback and whole-store rewriting. This limitation also needs to appear in the user-facing storage documentation. Power-loss guarantees are explicitly limited.

Reciprocal inspection of Skye's CLI/report found correct under-lock replay validation and report preservation of complete review/verification payload history. The current full-object category arrays match CLI/report expectations. Two follow-ups for Skye: bounded input reading should loop until EOF/limit rather than assume one FileHandle.read fills the buffer; the integration test needs a populated lead/evidence/review/negative-verification round trip so count/category/history regressions are observable. Existing progress-only integration does not exercise those paths. Reports appropriately disclose that artifact digests are references and free text is not automatically sanitized.
