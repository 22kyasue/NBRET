# ARTEX-core minimum acceptance experiment

Iris, 2026-10-21. Design/source review only for Cass. Only this document is authored. No ARTEX, target, provider, browser, build, installation, test suite or model was executed; no credentials read, shared source edited or commit made. The requested direction is ARTEX as candidate engine and operator UI, with our research methods, owned controls, independent effect checking and canonical client report retained. No competing engine/dashboard is proposed.

## Question and bounded conclusion

Can the actual admitted ARTEX configuration perform a coherent investigation on the existing owned local order application, retain attributable evidence, and produce a conclusion consistent with independent secure/disclosure controls, while stopping all owned activity? This first experiment establishes functional integration and bounded guided behavior. It cannot establish general autonomous discovery, expert superiority, independent custody, a production repair or readiness for autonomous TOBIRA activity.

Use one ARTEX task per fresh target generation, one planner and one worker, one explicitly selected provider/model path, and only the existing local HTTP/mail capabilities. Extra workers, scanners, browser adapters, skills and arbitrary helpers are unnecessary for this question. A screenshot proves an interface exists; the saved source proves selected paths exist; neither proves an operational configuration.

## Missing resources: resolve before first execution

1. **Reproducible runnable ARTEX and frontend:** identify full checkout/image, actual revision, local bridge hashes, norma dependency and frontend assets, database/runtime requirements and currently active configuration. The selected snapshot and screenshot alone cannot supply this. Do not install/build/start anything under this design assignment.
2. **Explicit execution admission:** exact owned environment, chosen model/provider and existing account entitlement, call/spend/time limits, permitted data and process owner. The bridge still sends history to provider services; “local” is not offline. No silent paid fallback or credential export.
3. **Reachability without widening scope:** the fixture currently belongs to KotaroPC; ARTEX was located on KrisPC and may run in another namespace. KrisPC's `127.0.0.1` is not KotaroPC's target, and host loopback is not guest/container loopback. Prefer co-locating the disposable fixture, typed executor and ARTEX tool-dispatch environment within one admitted namespace; transferring/starting that fixture is separately assigned, not done here. Otherwise require a separately admitted narrowly mediated route. Do not rebind target to `0.0.0.0`, create a public tunnel, expose it remotely or use host-control connectors as an implicit workaround. Existing transport permits literal exact loopback origins only; a changed topology requires a separately versioned decision. A network route alone does not integrate target requests with collector identities and the oracle: the tool-to-session adapter and verified build/generation mapping are distinct acceptance requirements.
4. **Actual all-path executor restriction:** demonstrate supported ARTEX tool registration/configuration and external scope/resource enforcement for SDK tools, custom tools, MCP and engine enrichment. No shell/MCP fallback around a rejected request. A named tool allowlist without enforcement is insufficient. If this cannot be demonstrated, record blocked integration rather than run unrestricted ARTEX.
5. **Small evidence bridge, not a new investigator:** a supported ARTEX tool invocation must reach `openLabSession` typed requests, preserve original ARTEX execution identity and return useful safe observations. The existing CLI hides root HTML and guide fields in serialized receipts, so feeding only its current output may prevent URL discovery. Define a reviewed safe public-page/protocol observation projection or mark discovery unsupported; never pretend a digest recovers omitted HTML. No such adapter is implemented here.
6. **Operator-only scoring/reset channel:** target descriptor, `inspect`, source/mode, oracle and replay access remain outside the investigator interface where feasible. If one unrestricted account exposes them, label the trial guided/familiar even when not deliberately shown.
7. **Stop supervision and storage:** identify task/worker/provider child ownership, pending queues, cancellation/termination verification, retained export locations and redaction policy. Do not terminate unrelated processes or rely on pause labels.

## Smallest staged experiment

Predeclare the sequence and budgets before seeing results. Suggested first cap: one planner/worker, at most 100 target/inbox requests, 256 KiB aggregate response bytes and three-second per-request timeout, matching existing transport defaults; ten-minute outer trial deadline matches the current interactive session. These are conservative proposal values, not validated sufficient investigation budgets. Fix provider-call and monetary caps separately before admission; ARTEX turn counts are not requests or spending. Reserve cleanup time outside the investigation window. Unsupported budgets mean blocked admission, not unlimited execution.

**A — integration baseline, no discovery claim.** On fresh secure and gap generations, an operator executes the already specified six-receipt scenario through the same proposed adapter/executor path that ARTEX will use. This is a plumbing/effect baseline, not an expert baseline. Expected results are secure `not-demonstrated`, gap `demonstrated`, matching legitimate owner access and anonymous denial. Include inert adapter mutations (wrong identity/object/build/generation, duplicate/missing/partial/redacted receipts) yielding `inconclusive`; verify a deliberate failing assertion is actually reached. Do not run the old scripted suite and call it ARTEX execution.

**B — actual ARTEX guided compatibility, two fresh tasks.** Let ARTEX's real planner/worker/model select and dispatch admitted typed tools. Give a public goal such as: “Explore the owned app's ordinary workflow; assess whether users can read only their own orders; preserve controls/evidence and uncertainty; no finding is required.” Supply exact scope, test account/inbox allowances, budget and cleanup constraints, not precreated target credentials. Declare this ownership-rule hint as assistance. Registration, actual delivered local mail, verification, normal use and `/api/me` corroboration remain real operations. Existing `verify-mail` is an explicit workflow helper; disclose its use instead of claiming ARTEX inferred every step.

ARTEX may discover no issue, choose another hypothesis, or fail to complete setup. Record that outcome without forcing a finding or inserting missing probes after the fact. Once its conclusion/submission is frozen, an operator may execute separate controls/replay against that generation; tag those requests **reviewer-produced**, never ARTEX-discovered evidence. Preserve original misses and reporting errors.

**C — challenge, report and cleanup.** A separately named reviewer, initially reading frozen submissions and actual receipts, checks both controls and contradictory cases. Fresh replay has new receipt IDs and belongs to the reviewer lane. Export actual ARTEX findings/graph/tool executions/traffic together with adapter evidence and canonical report projection. Shared-host review remains guided corroboration. Then apply the stop protocol below. If A fails, do not proceed to B; if B fails, C still retains failures and cleans up.

This is two tiny known-target trials, not a discovery benchmark. An additional minimally hinted target trial can be useful familiar practice, but withholding the literal mode name from this same source-aware session does not make it blind. Header/build IDs, response behavior, prior prompts and source exposure can reveal variants. A held-out evaluation requires inaccessible preparation/scorer material and admitted fresh families; no such custody is established here. Expert comparison requires a separately qualified human with matched access, assistance and budget, not a scripted baseline or Kotaro's guided learning.

## Evidence-adapter contract

Store original exports and a versioned mapping; do not rewrite ARTEX's schema or overwrite source evidence. Required envelope: evaluation run/attempt ID; ARTEX task/exploration/intent/worker/tool-call IDs; standalone finding ID **and** finding-node ID; tool name/version and actual inputs; request/response timestamps and monotonic ordering if available; engine/bridge/model/tool/config/source hashes; target build/generation/exact origin; collector identity/version; and simulation/error/truncation/completeness flags. Unknown fields stay unknown. Domain/time proximity cannot prove task attribution.

Each admitted HTTP observation must include the original transport receipt `{id,identity,request:{method,url,headers,body},response:{status,headers,body,bodySha256,bodyFieldsOmitted,bodyRedacted},complete,error?}` and a collector-verified `buildId,generation` from the operator descriptor and actual response headers. Nonsecret identity labels must map to authenticated `/api/me` user IDs and ephemeral session use; no Authorization/Cookie/token/password values enter exports. Preserve target/mail delivery correlation without exporting verification tokens. Record raw digest scope (body bytes versus ARTEX request/response snapshot bytes); do not equate differently scoped hashes or rehash redacted text as original bytes. Original raw bodies, if retained at all, need a separately controlled private store; digests alone are not an archive.

The existing oracle needs six distinct complete same-build/generation/origin receipts: `ownerCreate`, `ownerRead`, `otherRead`, `ownerMe`, `otherMe`, `anonymousRead`; plus distinct `ownerIdentity`, `otherIdentity` and declared `buildId`. It checks actual user IDs, exact object/path/payload, owner create201/read200, anonymous structured denial, and rejects omission/redaction/error/partial/mixed/duplicate evidence. A foreign403 carrying the exact order still demonstrates disclosure. Missing controls are inconclusive, never inferred from ARTEX prose. If the original ARTEX traffic store lacks the required identity or body, retain it as supporting evidence and use collector receipts for the oracle; do not synthesize facts into its snapshots.

Freeze ARTEX evidence/report versions and original bytes/digests using its existing export mechanisms where verified. Keep mapping from original traffic/snapshot/binding IDs to collector receipt IDs explicit and validated; reject ambiguity. Report `binding missing`, `body unavailable`, `version stale` or `identity uncorroborated` distinctly. The adapter only translates evidence and applies the existing rule; it does not plan investigations or award itself independent authority.

## Acceptance and failure criteria

| Dimension | Pass evidence | Non-pass meaning |
| --- | --- | --- |
| UI/plumbing | Actual task appears, controls dispatch, tool events and saved artifacts resolve to original IDs | Screenshot/rendered demo alone is untested; missing/incorrect IDs fail integration |
| Model/tool compatibility | Actual selected provider round trip parses representative ARTEX schema/history; returned tool call reaches intended executor; result returns to next decision | Auth/rate/schema/queue/timeout errors retained as compatibility failures, not target safety |
| Effect accuracy | Same-path baseline reaches secure denial and gap exact disclosure with positive/anonymous controls; adversarial evidence mutations reject | Missing/wrong controls inconclusive; false secure finding or false clean gap conclusion contradicts this selected control |
| ARTEX investigation | Frozen real action trace shows what it selected and found, including misses/unsupported coverage and hints | No finding is acceptable; missing discovery in gap is a recorded miss if access/control confirmed, not concealed by later replay |
| Review/promotion | Named challenge links exact observations, uncertainty and dissent; canonical report preserves bounded conclusion | Self-reported success or text/traffic binding alone cannot become independently verified finding |
| Stop/reset | Pending work fenced, owned activity settled, target/mail listeners refused, fresh generation empty | Pause/timeout/close label alone insufficient; unresolved activity is failed cleanup and blocks next trial |

No finding-count quota. Repeated two-mode successes establish these known controls only. Preserve eligible/attempted/completed/blocked/unsupported/inconclusive counts and full operator/setup/review/report labor. Stronger discovery-quality claims require independently adjudicated unfamiliar cases and a matched expert baseline. This experiment is not a real changed-build repair: secure and deliberately vulnerable modes are distinct controls.

## Promotion and stop rules

ARTEX findings first become imported **candidates** with source IDs and original wording. Exact local oracle evidence can support a guided reproduced effect in the canonical owner-action category. Missing/contradicted claims remain leads or rejected/contradicted records with reasons. Preserve `verifiedFindings:[]` unless the existing independent authority contract is actually met; a report-agent binding or second model opinion does not supply it. Owner policy, bounded consequence, remediation recommendation and actual repair/retest state remain separate fields.

At budget/expiry/error or operator stop: fence new target requests first; request ARTEX pause/cancellation for task/planner/worker/chat, cancel provider/bridge work and pending queues; await or explicitly terminate only owned supervised processes under the admitted hard bound; retain undelivered/late events; observe active requests/handlers/connections and owned process descendants; close target, inbox and SMTP and probe all three owned listeners for refusal. A direct `child.kill()` call does not prove descendants stopped. Verify no stale queued call can execute against a new generation. Start reset only after quiescence; observe empty account/order/mail state and invalid old sessions, then close reset resources too. An uncontrolled path or security rejection stops that lane without reassignment or bypass.

Minimal next decision: resource/configuration inspection and a narrowly owned ARTEX-to-existing-session evidence adapter admission. Do not adopt ARTEX automatically, start live-site autonomy, build another engine, or expand permissions to make this acceptance pass.
