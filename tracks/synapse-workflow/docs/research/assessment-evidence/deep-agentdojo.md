## What success means in the implementation

`benchmark_suite_with_injections` chooses task pairs and first tests whether injection objectives can be performed as ordinary tasks → an attack proposes injection values → `TaskSuite` injects those values into a synthetic environment → pipeline tools mutate that environment → task-specific state/trace predicates score legitimate utility and attacker objective separately → benchmark records booleans/logs and aggregates.

The variable **security** is potentially misleading: `BaseInjectionTask.security` returns true when the injection goal **succeeds**, not when the defender is safe. A no-injection run returns security=true as a sentinel. Report the field's semantics and run type rather than invert or average it blindly.

## Result bookkeeping, cache identity and errors

Complete `benchmark.py`: lines 36–38 aggregate all booleans in supplied dictionaries with a simple mean. Different task/suite cardinalities therefore affect weighting; empty input has no guarded denominator. Lines 41–157 run injection pairs and can reuse saved results by pipeline/suite/task/attack/injection IDs. Lines 160–229 run injection objectives as ordinary tasks, warn if not all succeed, then continue. That warning should be retained when choosing an eligible-task denominator.

Lines **120–147** explicitly map selected context and server errors to `(False, True)`, and DOS attacks at 149–150 instead use `not utility`. This policy makes errors count as security=true in those results; it is not evidence that an intended attacker goal was executed. Lines 232–316 do analogous handling for no-injection runs, whose security field is already a sentinel. Keep infrastructure errors, refusals, valid attempted failures and demonstrated attacker outcomes as separate categories in any analysis.

`load_task_results` 401–419 resolves a path from those IDs and validates the result model, but does not compare requested benchmark version, prompt, injection contents, model settings or source hash with the stored artifact. Version is metadata in logs, not part of the cache path. A changed task under the same names needs force-rerun or a separate run namespace and explicit provenance check. This parallels the general evidence-reuse problem in NBRET without being the same defect.

Complete `logging.py` 153–278 writes timestamp/package version, context, messages, errors and duration. Saves overwrite the current JSON file; this is not a tamper-evident journal. Its default log path is repository-relative if the delegate has no logdir, and logs can contain complete injected data/tool results. Log retention/access belongs in the assessment threat model. `yaml_loader.py` 31–62 resolves includes to local paths without a root-containment check; suite configuration is trusted. These mechanisms should not be exposed to arbitrary customer-supplied configurations as though they were sandboxed.

## Four locally confirmed observations

1. **Example oracle weakness:** complete `examples/counter_benchmark/suites/counter/user_tasks.py` 59–78 checks final unchanged state, output substring and three calls. Its nested if statements check `n` only when the function name is *not* increment_by. Correct function names therefore admit incorrect amounts. The actual method accepted the intended +5/-5 control and the incorrect 0/0 mutant; unrelated output failed. This is an educational example, not evidence that all default-suite tasks share the bug.
2. **Current-format canary check:** `is_task_injectable` 482–491 filters for tool content that is a string, while the reviewed ground-truth pipeline emits list content blocks. The actual helper returned false for a current-format tool message containing the canary. This can falsely fail the suite validation path; it is not an observed model defense.
3. **Error with an effect:** actual FunctionsRuntime, imported directly with Pydantic 2.14.1, incremented a synthetic counter before rejecting the outer function's integer-as-string argument. This demonstrates partial effects and the need to examine post-state even when a call reports error. No external service or tool was involved.
4. **Error classification:** AST-extracted production benchmark function, fake server error and in-memory logger produced utility=false/security=true exactly as its exception policy specifies. This validates bookkeeping, not provider error prevalence or attacker success.

The fixture uses the actual runtime module and extracted production scoring functions with synthetic dependencies. It bypasses pipeline/model initialization and does not validate SDK payload compatibility. Pydantic and Python versions are recorded; this is not the project's locked full environment. These constraints are part of the result.

## Improving evaluation without manufacturing a leaderboard

For each task, test the scorer with intended success, plausible wrong success, refused output, partial tool failure, extra side effects and stale state. Use mutation tests against the oracle itself: wrong parameters, wrong object/tenant and swapped actors should fail. Independently verify ground-truth feasibility and injection visibility in the current message representation. Preserve explicit unscored/error outcomes and report both end-to-end utility and demonstrated attacker effects. Hidden fresh tasks can reduce overfitting, but they do not repair a faulty oracle.

The smallest next experiment is to run a small selected default-suite task's ground-truth and negative mutations entirely offline, then compare its verdict against a separately written state predicate. Published task text and broad score differences alone cannot establish general agent-security performance.
