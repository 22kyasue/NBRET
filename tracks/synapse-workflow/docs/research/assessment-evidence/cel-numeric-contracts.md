## Different operations promise different precision

overflow.go302–317 rejects nonfinite doubles and out-of-range signed/unsigned conversions, then casts to the integer, permitting fractional truncation. The lossless helpers399–429 add a round-trip float comparison and are the actual helpers used by previously read list indexes and map numeric fallback. Thus int(4.2) and treating4.2 as an exact map/index integer are different contracts. double_test.go248–354 explicitly expects4.2→4 and4.7→4u while rejecting NaN/infinity/boundaries. It also deliberately expects float64(MinInt64)→error292–296, matching the helper's <= lower bound303; do not call this an accidental uncovered endpoint without checking intended semantics.

Mixed equality/order compare.go23–49 boundary-checks and converts the integer to Double. Int.Equal215–229, Uint.Equal184–198 and Double.Equal158–175 actually use those helpers. For sufficiently large adjacent integers, float conversion can erase distinctions; this is a source-level precision limitation, not an observed wrong authorization result. Whether a policy uses numeric identifiers, the input's original integer precision and application coercions must be known before claiming impact. Exact same-integer comparisons do not take that float path. NaN is explicitly rejected for Compare by each primitive and returned false for Equal; compareDouble69–77's fallthrough-zero alone does not establish NaN compares equal in these callers. The standard library additionally guards NaN before order comparisons, as read earlier.

Int.ConvertToNative82–107 uses the int32 checked range for both Go int and int32; Uint.ConvertToNative76–97 similarly uses uint32 for Go uint. Those constraints apply even on a64-bit platform; they are distinct from Int64/Uint64 conversions. Named types convert through reflection after the width check. Pointer support is specifically enumerated, rather than all pointer widths inferred from direct-value support. No overflow or architecture fixture was executed. Native field construction propagates these conversion errors in the previously traced NewValue path.
