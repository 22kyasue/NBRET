## REA: preserve the physical read and cleanup outcome

Repository [morluto/rea](https://github.com/morluto/rea), commit `54c71313aeb2cbdf21626af9557673a6f6397180`, MIT. The eight files in `source-reading.json` and LICENSE were read completely with numbered output, without clipping. No upstream tests or runtime providers were executed.

Trace: `readWebArtifactJson` → `readStableArtifact` → `withArtifactFileHandle` → `withOwnedFileHandle` → `OwnedFileHandle.close`. The JSON caller then decodes UTF-8 and calls `safeParseJson`.

- [WebArtifactReads.ts lines 29–60](https://github.com/morluto/rea/blob/54c71313aeb2cbdf21626af9557673a6f6397180/src/browser/assets/WebArtifactReads.ts#L29-L60): fatal UTF-8 decoding, stable bounded read and explicit JSON parse outcome. A digest is over the original bytes, not reparsed JSON. Lines 62–165 distinguish cleanup, cancellation, selected-path, OS, format and adapter errors; they do not turn all failures into “not found.” `safeJson.ts` lines 7–17 catches JSON parsing failures and retains the cause; it does not validate a domain schema.
- [readStableArtifact.ts lines 50–92](https://github.com/morluto/rea/blob/54c71313aeb2cbdf21626af9557673a6f6397180/src/artifacts/readStableArtifact.ts#L50-L92): checks cancellation, regular-file status, size and opened-file identity. Lines 93–115 enforce a streaming byte budget. Lines 116–141 compare identity, size and timestamps after reading, check byte count, and only then return bytes and SHA-256. Lines 28–48 reclassify selected disappearance/link errors after initial validation as integrity failures.
- [ArtifactFileOperation.ts lines 227–268](https://github.com/morluto/rea/blob/54c71313aeb2cbdf21626af9557673a6f6397180/src/artifacts/ArtifactFileOperation.ts#L227-L268): binds a concrete descriptor owner and cleanup lease to the operation; propagates typed cleanup/cancellation failures. Lines 23–92 preserve the physical operation outcome alongside cleanup problems. These are code paths, not a promise in a model prompt.
- [OwnedRegularFile.ts lines 129–181](https://github.com/morluto/rea/blob/54c71313aeb2cbdf21626af9557673a6f6397180/src/filesystem/OwnedRegularFile.ts#L129-L181): captures operation success/failure, attempts close in either case, retains failed close ownership and handles cancellation after a completed read. [OwnedFileHandle.ts lines 17–43](https://github.com/morluto/rea/blob/54c71313aeb2cbdf21626af9557673a6f6397180/src/filesystem/OwnedFileHandle.ts#L17-L43) distinguishes closed, closing, failed and retryable-open states. An invalidated descriptor is not silently counted as confirmed cleanup.
- [ArtifactResourceScope.ts lines 91–185](https://github.com/morluto/rea/blob/54c71313aeb2cbdf21626af9557673a6f6397180/src/artifacts/ArtifactResourceScope.ts#L91-L185): prevents admission after close, tracks active operations, retries pending cleanup and reports retained failures. Lines 189–212 dispatch cleanup by owner kind. `RegularFile.ts` lines 72–122 separately implements regular-file admission and Windows fallback checks; this is a neighboring path, not a claim that `readStableArtifact` calls `openRegularFile`.

**Implication:** a claim may carry “physical read completed, cleanup failed” rather than losing the observation or falsely declaring success. **Limits:** metadata and digest checks do not prove authenticity, tenant authorization or resistance to a hostile filesystem with stronger powers. Platform flag semantics and all caller path validation remain separate concerns. Exception types, cleanup-lease internals, every caller and parser dependencies were not exhaustively traced. This review establishes the inspected flow only.

## Atomic Red Team: a technique label is too coarse for authorization

[redcanaryco/atomic-red-team](https://github.com/redcanaryco/atomic-red-team), commit `388942adbd9641f4dfdcf079d7efe9a75ec0ac43`, MIT. Complete file [T1078.001.yaml lines 1–80](https://github.com/redcanaryco/atomic-red-team/blob/388942adbd9641f4dfdcf079d7efe9a75ec0ac43/atomics/T1078.001/T1078.001.yaml#L1-L80) and LICENSE.txt were read. YAML SHA-256: `fa2d73270cd534e7edb1c121e908623bba4668652d6f48126da916e79c788d01`. Nothing was executed.

Lines 4–31 identify one Windows test and input defaults. Lines 32–48 describe an elevated executor changing a guest account, group membership and RDP-related registry state. Cleanup lines 40–46 are conditional; the default argument leaves the optional RDP removal disabled. The file also describes narrower Windows and macOS tests in lines 50–80. None of these declarations proves telemetry or alert generation.

The correct approval unit is the exact test, arguments, environment and intended effects. Cleanup needs baseline comparison: disabling a guest or deleting settings can itself fail to restore a pre-existing state. An executor may stop partway, so command lists need per-effect receipts. The runner and prerequisite expansion are outside this review; do not infer their failure handling from this YAML. This is useful evidence for the infrastructure threat model, not a recommendation to run these tests on this PC.

## Microsoft Sentinel: an explicit detection data contract

[Azure/Azure-Sentinel](https://github.com/Azure/Azure-Sentinel), pinned file-affecting commit `cbb05d9204c89a9d83d8ec69b59dea4fc9b207a8`, MIT. [ExchangeFullAccessGrantedToApp.yaml](https://github.com/Azure/Azure-Sentinel/blob/cbb05d9204c89a9d83d8ec69b59dea4fc9b207a8/Solutions/Microsoft%20Entra%20ID/Analytic%20Rules/ExchangeFullAccessGrantedToApp.yaml) and LICENSE were read completely. Selection receipt: [sentinel-pin.json](sentinel-pin.json). Rule version is 1.0.2. This is a pinned historical implementation, not a claim that it is every tenant's deployed rule.

Lines 8–15 require AuditLogs and specify hourly frequency/period with a positive-result threshold. Lines 22–26 select directory application-management consent events and the permission string. Lines 27–49 expand resource/properties and extract fields. Lines 51–52 parse a particular permission-string layout and filter the extracted scope. Lines 53–60 derive initiating identity and address; lines 61–94 map entities and alert context.

The text describes admin consent, but the inspected query extracts `AdminConsent` without a separate explicit truth filter. This is a schema/semantic question to validate, not evidence of a vulnerability. Missing or changed properties, another permission serialization, pre-existing grants or late ingestion can affect results. A representative local replay should include realistic positive events, benign grants, schema variants and late arrivals. No KQL backend was available or exercised here; this review does not establish detection performance. A mapped ATT&CK technique and an available rule are weaker evidence than a produced event, matched alert and verified response.

## Benchmark documentation: different questions need different oracles

The [AgentDojo README](https://github.com/ethz-spylab/agentdojo) describes suites, user tasks, defenses and attacker configurations; it is evidence of the benchmark's documented structure, not measured effectiveness in an assessment platform. The [PurpleLlama benchmark README](https://github.com/meta-llama/PurpleLlama/tree/main/CybersecurityBenchmarks) was only partially read: its introductory task taxonomy and evaluation instructions distinguish prompt injection, exploitation, code generation and defensive tasks. In particular, response/judge-based tasks cannot be treated as successful tool action. These documentation reads did not inspect scorer correctness or run either benchmark.
