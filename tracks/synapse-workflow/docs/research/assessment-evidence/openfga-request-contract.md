# Controller follow-through: narrowed concerns and contrary evidence

The broader freshness limit is established separately. DetermineInvalidationTime returns zero on a missing/invalid changelog entry while triggering asynchronous work, explicitly permitting cache use while refresh is pending (controller150–194). The refresh creates a background context and a one-second timeout, reads descending changes, and on a read error invalidates the store's iterator cache (241–288); timeout returns without updating it, leaving a future refresh attempt. Normal completion records the newest change timestamp and chooses full versus per-entity invalidation based on the newest batch and iterator TTL window (290–358). A missing cache hit is not synchronous verification against the latest database write. This is the source's explicit eventual-consistency tradeoff, not a newly measured stale-read duration.

Tests29–268 distinguish cache hit within refresh interval, hit after interval, miss returning zero, and subsequent refresh. Tests286–566 check expected cache writes for timeout, changelog errors, full and partial invalidation; the mock timeout sleeps beyond the controller timeout, and the runner then waits for the controller wait group. Their partial-invalidation fixtures use simple user strings; full userset-string behavior here is established by the traced code, not a runtime test.

Ordering concern also narrows for two actual adapters: `pkg/storage/postgres/postgres.go` 779–824 always orders reverse reads by object_id with C collation; `pkg/storage/mysql/mysql.go` 439–485 always orders by object_id.
