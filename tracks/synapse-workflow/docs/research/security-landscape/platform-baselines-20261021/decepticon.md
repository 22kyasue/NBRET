## Actual autonomy and communication

The [orchestrator factory](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/packages/decepticon/decepticon/agents/standard/decepticon.py#L73) builds a LangChain/LangGraph agent, default recursion limit 400. It discovers specialist factories through registered plugin entry points and wraps them for streamed events. Its ordinary domain tools are deliberately empty: work is delegated through `task`; conditional `ops_*` tools expose infrastructure control when the daemon socket exists. This is more than a fixed scanner chain: the model selects specialist tasks and reacts to their outputs within the available workflow.

[Middleware assembly](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/packages/decepticon/decepticon/agents/middleware_slots.py#L167) wraps the supervisor's task tool with OPPLAN dispatch and preserves subagent transcript state. [Dispatch validation](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/packages/decepticon/decepticon/middleware/opplan_dispatch.py) binds task ID, plan revision and specialist type, checks executable leaf/prerequisites and propagates workflow configuration. Communication is delegated task context, returned outcomes, durable artifacts/transcripts and shared engagement state; this is not evidence that every specialist independently discovers or validates a fact.

The [OPPLAN DAG contract](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/docs/red-team/opplan-dag.md) distinguishes findings, no-findings, blocked/inconclusive infrastructure and revoked prerequisites. Dependencies can be satisfied by existing source/access rather than forcing a kill-chain ladder. This is a valuable coverage model. An existing evidence file can satisfy a structural prerequisite without proving its contents true. The [extension contract](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/docs/design/extension-contract.md) distinguishes workflow selection from capability and authorization, freezes workflow versions/hashes, and warns that explicit middleware overrides replace the standard stack. Review actual resolved plugins/configuration before making any deployment claim.

## Inputs, accounts, browser and memory

The [engagement workflow](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/docs/engagement-workflow.md) permits a direct Red engagement from an approved root URL; the seven-document planning workflow is optional. Provided source, captures or access may supply prerequisites. Thus URL-only investigation and source-assisted investigation must be reported separately. Account creation, mailbox custody, verification links, principal switching and protected credentials are not solved merely by accepting a URL or a workspace. This study did not establish a general mailbox integration or safe production-account onboarding.

The [browser tool](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/packages/decepticon/decepticon/tools/browser/tools.py#L1) multiplexes persistent browser actions including navigation, click/type, screenshots, page source, JavaScript and tab management. It includes native-browser routing imports and a Playwright session implementation. Errors become structured tool results, letting the agent continue. Lazy dependency availability is a real setup condition. `_safe_close` bounds each close and logs failures; abandoning a hung handle after timeout is not proof that its process disappeared. This is not a runtime compatibility check with Kotaro's computeruse harness.

[Knowledge-graph middleware](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/packages/decepticon/decepticon/middleware/kg.py#L1) exposes engagement-bound recording/ingestion, injects middleware-controlled provenance and refreshes summaries on revision changes. Files, checkpoints, skills and model summarization also carry context. These support persistence and hypothesis organization; they do not demonstrate improved discovery, trustworthy learned policy or resistance to poisoned observations. A model-authored graph observation remains an observation with a source, not automatically an independently confirmed effect. Blue sensor mode is documented, while the broader attack/defend/verify loop remains planned.

## Verification and reporting

The [standard verifier prompt](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/packages/decepticon/decepticon/agents/prompts/standard/finding_verifier.md) is a strong reusable method: another agent's conclusion is input, fresh positive and comparable negative/control evidence are required, identity/reachability matter, and unsupported findings remain unverified. It separates verified negative results from vulnerabilities and false positives. Browser-dependent claims require actual browser behavior. Those are instructions to a model, not a deterministic universal effect oracle.

The [reporter factory](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/packages/decepticon/decepticon/agents/standard/finding_reporter.py) limits its role to filesystem reporting plus quality/CVSS tools. The [finding checker](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/packages/decepticon/decepticon/tools/reporting/finding_quality.py#L34) explicitly says it never judges exploit truth. It checks canonical IDs, verdict/result kind, rationale, sections, evidence path existence and computed CVSS consistency. A complete report can therefore be structurally valid without the underlying effect being established.

The [local evidence contract](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/docs/tools/local-evidence-contract.md) is particularly candid: path/access validation does not inspect content, and the optional surface is not wired into all existing execution/export paths. [Scoped reporting I/O](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/packages/decepticon/decepticon/middleware/scoped_reporting_io.py) adds size limits and trusted workspace/tool bindings for its specific reporting lane. Neither constitutes universal immutable raw-response custody or a same-build identity/object oracle. ARTEX's native artifacts should first be inspected against our existing six-receipt owned-control evaluation; do not build a parallel reporting system from these patterns.

## Scope, deployment and stop: conditional mechanisms

The current [backend factory](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/packages/decepticon/decepticon/backends/factory.py) is **HTTP-only**. Endpoint/token resolution can come from explicit configuration, ambient run configuration or environment. It caches by endpoint and token to prevent files and shell routing to different sandboxes. Older Docker-exec/socket architecture descriptions should not be applied wholesale. Current [Compose](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/docker-compose.yml#L190) removes direct Docker socket access from the agent path, but an optional CLI service still mounts it around line 509. Both declared networks are bridge networks; network names alone establish no target allowlist. Review the selected deployment profile, capabilities, tokens and actual namespace routing.

[RoE middleware](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/packages/decepticon/decepticon/middleware/roe.py) distinguishes audit, warn and enforce. Missing/invalid configuration falls back to audit; warn can execute a disallowed call and append a warning. Enforce refuses matching gated tool calls, checks the abort marker, and includes request pacing/concurrency controls. Parsing selected commands/tools is not comprehensive network mediation. The [egress compiler](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/packages/decepticon/decepticon/middleware/egress.py#L102) enables default-drop only with enforce mode **and a nonempty in-scope allowlist**, and adds OSINT provider exceptions. RoE egress provisioning around line 470 is best effort: an exception is logged and execution continues, with later retry possible. This is a source-observed assurance limitation, not an observed escape. Our stopped actions must not be rerouted just because a refusal prompt suggests another technique.

[HTTP execution cancellation](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/packages/decepticon/decepticon/backends/http_sandbox.py#L334) uses a thread wrapper; remote work may become a tracked background job after client cancellation. Explicit `kill_session` calls the daemon and clears the mirror tracker. Client cancellation is consequently not synonymous with quiescence. The [launcher stop command](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/clients/launcher/cmd/stop.go) tears down Compose and then the infrastructure daemon; a daemon-stop error is a warning before its success message. Full descendant/remote workload termination was not traced end to end here. Any owned exercise needs observed absence of listeners, jobs and subsequent requests, including after interruption; no command was run by this audit.

## Models, compute and cost

Factories resolve role models and fallback chains; recursion limits bound graph steps rather than dollars or total target effects. The deployment includes LangGraph, sandbox, optional Neo4j and model/proxy services: this is not a dependency-free script. Browser extras and optional workload profiles add dependencies. Provider/account configuration and actual model tool compatibility remain deployment questions.

[Budget middleware](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/packages/decepticon/decepticon/middleware/budget.py) checks engagement/per-agent USD spend before model calls using cached proxy accounting. Caps default to zero/disabled. Configured caps reject known unpriced fallback routes and unavailable credential inventory, a useful defense. However, spend-provider exceptions around line 329 skip enforcement that turn; the default query path can return zero on failure around line 411. Polling and concurrent/in-flight calls also preclude interpreting this as an exact prepaid ceiling. No locally observed cost or performance is available.

## Evaluation strength and contrary evidence

At this pin the [published result index](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/benchmark/results/README.md#L1) claims **102/104 (98.08%), cycle-4 final**, comprising 45/45 easy, 50/51 medium and 7/8 hard. This supersedes interpreting the older easy-only 45/45 headline as the whole current claim. It explicitly provides vulnerability tags as hints, and links winning traces. These are maintainers' published results, not our reproduction or an independent evaluation. Winning-run aggregation over cycles must not be presented as first-attempt held-out accuracy.

The [benchmark method](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/benchmark/README.md) injects challenge metadata/flag format and drives the actual delegation pipeline. The [XBOW evaluator](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/benchmark/providers/xbow.py#L212) compares a flag parsed from emitted output against a challenge-derived expected value. This is narrower than arbitrary business-policy or ownership-effect verification. Expected values are deterministically derived from public challenge IDs in this harness, making strict scorer/source separation important; this study establishes no cheating or actual contamination. Keep this public benchmark checkout outside any investigator retrieval/context for a future held-out exercise.

The [scorer](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/benchmark/scorer.py) aggregates supplied passed results; partial captured costs can become a subtotal. The [cross-project table](https://github.com/BitterSecurity/Decepticon/blob/b2d1080d605249f8ed48cfd87a95563eb3397fb1/docs/benchmark-comparison.md) itself acknowledges differing source access and hint levels. Its other projects' headline numbers were not independently validated here and are not a controlled ranking. No inspected study establishes secure-negative specificity, arbitrary unfamiliar-site coverage, client-policy understanding, monitored-regression effectiveness, expert parity or protected account/mail custody. The historical 72 local checks likewise measure implementation behavior, not discovery accuracy.

## What ARTEX can borrow, and what remains a question

1. Borrow explicit task prerequisites, revision-bound workflow selection, revoke propagation and typed blocked/no-finding outcomes. First map these to ARTEX's actual native states; no new orchestrator is justified.
2. Borrow the verifier's fresh positive/control discipline and reporter/verifier role separation. Keep effect promotion dependent on independent receipts and policy, not a model's verdict or valid Markdown.
3. Borrow source-stamped engagement memory and uncertainty-preserving coverage. Evaluate usefulness before introducing Neo4j or cross-run learning machinery.
4. Borrow explicit effective-tool/profile inventory and scoped artifact checks. Avoid assuming a prompt, audit default, named sandbox or optional firewall is a verified boundary.
5. Borrow interruption accounting: distinguish UI pause, graph termination, remote job termination and complete quiescence. Verify only the admitted ARTEX execution lanes, without expanding the first usable baseline into every conceivable deployment.

Concrete remaining questions are the actual ARTEX deployment/model/tool configuration, native export identifiers and raw artifact availability, routing and scope mediation, and stop behavior for enabled lanes. They are finite inventory/acceptance questions. Reproducing Decepticon's full stack, its benchmark score, all plugins or all research findings is not a prerequisite to an initial owned ARTEX exercise. No new adapter, UI, installation, target execution or stopped-operation resumption is proposed by this report.
