## Five finite inventory questions for the existing ARTEX baseline

These are the immediate decision inputs, extracted from Thistle's source-backed handoff. They can be investigated read-only; they do not require finishing every comparison or launching a service.

1. **Which instance/build?** Identify existing machine and launch provenance, non-mock frontend/backend, source/build version and binary/image identity. Known complete checkout is documented on KrisPC at `C:/Users/stake/synapse-security/artex-global`; the saved local reference is not a runnable checkout. Upstream mock screenshots must not be conflated with Kotaro's screenshot.
2. **Where does it run/store state?** Existing launch/config location, data store identity, mounts, listeners and host/container/PC boundaries, without passwords/DSN/environment dumps. Kotaro-PC loopback differs from KrisPC/container loopback.
3. **Which model/tools are configured?** Redacted active profile metadata, model/base host, worker/turn/time/token settings, tool/agent bindings, skill names/hashes and MCP command/transport metadata. Read files first; profile-test, model-discovery, MCP-refresh and tool-test can execute/connect and are not inventory substitutes.
4. **What contains and stops execution?** Existing OS privilege, mounts/network/resource policy, supervisor/restart configuration and mapping of chat stop, task pause and work cancellation. Read-only inventory cannot prove quiescence; later owned active-work observation is separate.
5. **What evidence can be reviewed/exported?** Existing neutral/redacted artifact/schema with task/finding/evidence IDs, hashes/length/completeness, principal/build fields and current review privileges. No new task, replay or retest just to obtain a sample.

Source anchors are in [ARTEX baseline, settings and deployment](artex-deep-baseline.md#settings-run-workflow-and-deployment-facts-still-missing), [stop operations](artex-deep-baseline.md#stop-is-several-different-operations) and [evidence lifecycle](artex-deep-baseline.md#evidence-and-reporting-reuse-the-native-lifecycle), with exact pinned upstream links. ## Staged decision review

First establish the real existing instance and native interfaces. Then decide whether configuration alone provides a usable baseline. Only a specifically missing observation/method/evidence field justifies proposing an additional tool or adapter. Owned-control engine exercises come after their actual execution topology, authority and limits are understood; current research does not start them.

For a later exercise, keep plumbing, observation-directed investigation and independent review separate. A scripted local rehearsal proves its collector path, not ARTEX discovery. Freeze engine output before reviewer replay; do not backfill missed discoveries. Native confirmed, model-voted, source-grounded, independently corroborated and report-ready are distinct states.

Getting ARTEX usable does not require claiming commercial readiness, global vulnerability recall, hidden benchmark separation, full account/mail autonomy or every integration's safety. Those claims need their own evidence when relevant. Conversely, an outer execution boundary and a meaningful stop are required before active investigation, not paperwork to postpone indefinitely.

## Cross-report reconciliation

Ginger and Iris reviewed the delivered studies specifically to prevent research from turning into unnecessary implementation prerequisites.

- **Norma is now source-reviewed.** Older statements that its runtime permission implementation was unread are superseded by Thistle's pinned review. Bypass preserves explicit deny/hard-denial checks and subsequent hooks; do not describe it as no checks. Actual deployed dependency/configuration remains unknown.
- **Native evidence is substantial.** Hash-checked body blobs and frozen traffic/report versions exist in source. The missing proof is effect/identity applicability in a real run, not a reason to replace native storage.
- **One research access path, if needed.** Existing native memory, skills, graph and context must be examined before proposing a RAG server, another memory store or a blackboard. Summaries/technique memory remain guidance, not observed target facts.
- **One browser capability, if needed.** DOM, visual, Magnitude, Playwright and Chromedp are alternatives for a concrete observation gap. Do not accumulate all of them or assume they solve dedicated-mail/identity custody.
- **Name the stop.** Chat stop leaves workers/planner active; task pause, individual work cancellation, deletion and process shutdown differ. Retain positive cleanup implementation as well as source limits. Review only actually enabled lanes for the first bounded exercise; do not require an audit of every unused integration.
- **Manual review can precede automation.** A neutral native export plus an explicit manual mapping into the approved reader is enough to assess report suitability. An automated report adapter, independently held-out benchmark and cross-tool superiority are later questions, not prerequisites for guided usability.

The smallest later operational sequence is: redacted deployment receipt, separately admitted inert model/stub compatibility check, one bounded existing owned control, frozen native submission, reviewer-produced effect/control observations, explicit manual canonical mapping and observed cleanup. Neither source reviewers nor this index have executed that sequence through ARTEX.

### Shannon addition

The current open-source Shannon requires source plus a running application URL; source-free black-box testing belongs to a separate commercial claim. Current Pi/Temporal source supersedes older Claude-SDK-only descriptions. Thus its supplied-source/admin benchmark is not comparable to ARTEX URL-first work without matching access.

Its useful additions to our method comparison are discriminated exploited/blocked/partial states, queue identity and duplicate checks, canonical artifact manifests, and stop outcomes based on directly queried workflow/container state with an explicit unverified result. These are source-supported strengths. Valid proof-text fields and consistent manifests still do not independently observe a business effect; confirmed closure of managed workflow/container state does not establish every external effect stopped. No new ARTEX installation, adapter or replacement is justified by this study.

### hackingBuddyGPT addition

Its current implementation contains real web/API and AD paths as well as Linux privilege-escalation use cases. The paper's prearranged low-privilege access, hints and Linux tasks are not a URL-first ARTEX comparison. The useful method is small explicit use cases with declared inputs, success predicates, history treatments, bounded worker capability sets and run traces.

Keep the positive live session UID/credential checks distinct from the same detector's output/prompt regex fallbacks; the latter's false-success possibility is source-predicted, not reproduced. Likewise parent accounting has settlement/helper/embedding exceptions, HTTP has no explicit synchronous request timeout, and missing price information can become zero. ARTEX should preserve exact effect checks, include settlement costs and record unknown spend rather than borrow blanket ground-truth, hard-deadline or free-inference claims. No extra RAG store, browser or engine follows.

### Decepticon addition

Its current agent sandbox path is HTTP-based, while an optional CLI profile still mounts the Docker socket. Audit versus enforce mode, a nonempty egress allowlist, provisioning failures and effective budget-accounting behavior change the actual boundary. A deployment name or latest architecture description alone is insufficient. These are source-supported conditional behaviors, not runtime escapes demonstrated here.

Borrow revision-bound prerequisites, typed blocked/no-finding outcomes, fresh positive/control verification instructions and reporter separation, mapped first to ARTEX's native states. The finding checker explicitly validates structure rather than exploit truth; client cancellation can differ from remote-job termination. The published cycle-4 102/104 result supplies vulnerability-tag hints and aggregates winning traces, so it is not independently reproduced one-pass held-out discovery. None of these comparisons blocks ARTEX inventory or requires installing the rival stack.
