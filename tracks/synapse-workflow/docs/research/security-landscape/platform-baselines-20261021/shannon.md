## Inputs: source plus running application

The ordinary OSS workflow expects a **local source directory and a running target URL**. CLI `resolveRepo` verifies the supplied path exists and is a directory; launch passes both target URL and repository mount into the worker. This check does not authenticate that the source matches the deployed target. [apps/cli/src/paths.ts:77–95](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/cli/src/paths.ts#L77-L95); [apps/cli/src/docker.ts:499–507](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/cli/src/docker.ts#L499-L507).

The target repository is mounted read-only, with writable run-specific overlays for deliverables, scratchpad and browser artifacts. This preserves much source content but is not a claim that the run is read-only: live target actions and workspace writes remain active. [apps/cli/src/docker.ts:453–487](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/cli/src/docker.ts#L453-L487).

Authenticated mode can take username/password, TOTP, mailbox credentials, explicit login steps and a success condition. Those are supplied access/preconditions, not automatically discovered identities or independently verified role ownership. Email login configuration supports existing magic-link/OTP flows; this review establishes neither an external mailbox service nor autonomous URL-only signup. The validate-auth mode performs a real login, so it is an execution action, not a harmless configuration check. [docs/configuration.md:60–81](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/docs/configuration.md#L60-L81); [docs/configuration.md:155–192](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/docs/configuration.md#L155-L192).

OSS source-assisted results must therefore be a separate evaluation arm from ARTEX URL-first self-registration. Do not quietly give target code, login instructions or privileged accounts to one contestant. No finding here establishes a missing ARTEX prerequisite: it clarifies evaluation fairness.

## Actual autonomy, tools and state

Temporal supplies a durable staged workflow. At this pin, optional agentic SAST overlaps initial work; pre-recon and recon run sequentially, then five fixed class pipelines run with a concurrency limit alongside a miscellaneous lane. Within a class, analysis is followed by reconciliation, queue selection and conditional exploitation. Per-class failures can become partial reasons while other lanes continue; cancellation propagates separately. [apps/worker/src/temporal/workflows.ts:740–807](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/temporal/workflows.ts#L740-L807); [apps/worker/src/temporal/workflows.ts:1397–1459](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/temporal/workflows.ts#L1397-L1459).

This is autonomous choice **within a predefined workflow and tool/prompt environment**, not an unrestricted research scientist that invents and validates every methodology. Configuration documentation says the five analysis classes are fixed; optional SAST adds source analysis/time/cost and its failure can leave a partial result. A miscellaneous exploitation lane broadens intake without changing that five-class analysis contract. [docs/configuration.md:108–125](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/docs/configuration.md#L108-L125).

The executor creates parent/child task tools, todo and glob tools, tracks child usage, creates in-memory model sessions with compaction, and connects activity cancellation to session abort. Browser-driving agents receive a Playwright CLI skill; other agents get no skills through this loader. The browser configuration writer prepares Chromium defaults unless a user config exists. Presence of that writer is not proof of a browser launch, UI correctness or compatibility with Kotaro's preferred computeruse harness. [apps/worker/src/ai/pi/pi-executor.ts:79–111](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/ai/pi/pi-executor.ts#L79-L111); [apps/worker/src/ai/pi/pi-executor.ts:283–352](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/ai/pi/pi-executor.ts#L283-L352); [apps/worker/src/ai/playwright-config-writer.ts:75–89](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/ai/playwright-config-writer.ts#L75-L89).

## Evidence, verification and reporting

Shannon's advertised proof-by-exploitation policy is useful as a methodological aspiration, but actual checks must be named.

The exploit collector has separate exploited and blocked schemas. Exploited requires nonempty impact, steps and proof-of-impact text; blocked requires confidence, current blocker and supporting explanatory fields. It rechecks schema, validates code-location path shapes, restricts IDs to the class namespace and current queue, and rejects duplicate submissions. These are concrete consistency checks. They do **not** independently observe the submitted impact or replay the claim against another principal/build. [apps/worker/src/collectors/exploit-collector.ts:354–390](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/collectors/exploit-collector.ts#L354-L390); [apps/worker/src/collectors/exploit-collector.ts:463–521](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/collectors/exploit-collector.ts#L463-L521).

The session-level exploitation validator returns true, because rendering occurs later; the source collector still performs the checks above. Thus “validator passed” cannot be presented as independent effect verification. The vulnerability-stage validator checks queue-file existence in its particular layer. This is a narrowly scoped code observation, not a claim that the entire reporting pipeline lacks validation. [apps/worker/src/session-manager.ts:146–173](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/session-manager.ts#L146-L173).

Finalization has valuable artifact discipline: it reads committed report JSON, canonicalizes it with exploit/partial-reason state, generates Markdown/SARIF, builds a manifest and writes exact output files under a repository lock. Coherent previous outputs can be adopted; SARIF rendering degradation is represented. PDF is a derived artifact with separate provenance. [apps/worker/src/services/report-finalization.ts:350–440](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/services/report-finalization.ts#L350-L440). These integrity checks authenticate output consistency, not truth of the underlying vulnerability.

The exploit-mode report adapter distinguishes status buckets and summaries. Blocked candidates exist alongside exploited findings in the broader pipeline, so the marketing phrase about reporting only proven issues must not erase blocked/analysis-only states. Analysis-only mode explicitly describes assessed severity/confidence rather than demonstrated impact. [apps/worker/src/services/report-json-adapter.ts:183–229](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/services/report-json-adapter.ts#L183-L229); [docs/configuration.md:127–151](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/docs/configuration.md#L127-L151).

For ARTEX, borrow typed evidence states, queue identity checks, partial coverage and canonical output receipts. Preserve ARTEX native IDs/versions and use our independent effect/control contract plus approved canonical reader. A second model, stricter JSON or artifact hash is not a substitute for independent target-effect evidence.

## Scope, isolation and stopping

Safety documentation warns of state mutation, unintended outbound traffic and adversarial-source prompt injection, and recommends a disposable VM. Those statements are restrictions/warnings, not code enforcement. [docs/safety.md:11–32](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/docs/safety.md#L11-L32).

Configuration validates rule formats and exposes avoid/focus/rules-of-engagement guidance. The inspected permission adapter specifically translates **code_path avoid** rules into an external permission-extension config, with default allow and external-directory access allowed. If there are no code-path avoids it removes that config. If the extension cannot be resolved, the executor warns and skips enforcement. Underlying extension coverage was not audited, so neither these comments nor schema acceptance establish complete file/shell/network containment. [apps/worker/src/ai/pi/permission-system.ts:69–126](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/ai/pi/permission-system.ts#L69-L126); [apps/worker/src/ai/pi/pi-executor.ts:79–93](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/ai/pi/pi-executor.ts#L79-L93).

The reviewed worker launcher joins a Docker network, mounts workspace/auth/output paths and sets container-wide seccomp unconfined for Chromium needs. This is a real isolation tradeoff, not an allegation of an observed escape. No complete mandatory network-destination gate was established by the selected paths. Do not transplant this deployment configuration into ARTEX merely because both use browser tools. [apps/cli/src/docker.ts:424–487](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/cli/src/docker.ts#L424-L487); [apps/cli/src/docker.ts:490–503](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/cli/src/docker.ts#L490-L503).

**The stop implementation is especially worth borrowing as a contract.** It requests cooperative cancellation, polls direct workflow state, performs bounded termination attempts, and returns unverified if closure cannot be established. Container stop is followed by a fresh query; query failure is unverified and remaining containers mean still-running. A successful request acknowledgement alone is insufficient. [apps/cli/src/commands/stop.ts:165–274](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/cli/src/commands/stop.ts#L165-L274).

That is source-level lifecycle verification, not proof all external effects ceased or remote systems were restored. Workflow cancellation connects to model-session abort/disposal, and cancellation logs are finalized separately; these do not independently prove child-process or network quiescence in an untested installation. ARTEX already has several cancellation paths; use this comparison to sharpen status semantics and owned-control observations, not replace its engine.

## Concrete ARTEX implications and unresolved questions

Borrow three methods: **(1)** source-to-runtime hypothesis linkage when source is explicitly admitted; **(2)** discriminated evidence/blocked/partial states plus stable IDs and output manifests; **(3)** cancellation outcomes grounded in direct lifecycle observations with an explicit unverified state.

Avoid three shortcuts: **(1)** equating source-plus-admin access with URL-only investigation; **(2)** promoting schema-valid proof text to independently verified effect; **(3)** treating a Docker worker, code-path rule or stop acknowledgement as complete containment/quiescence.

**Nothing discovered here blocks the existing read-only ARTEX deployment inventory.** Shannon is comparison research, not a prerequisite install. First resolve the already identified ARTEX instance/version/configuration/tool/network/stop/export facts. Later owned evaluations should freeze original submissions before reviewer replay, preserve failed and inconclusive cases, and match access and budget.

Unresolved: deployed-source correspondence; exact network/extension enforcement beyond the reviewed paths; complete activity/subprocess cleanup; all report-schema migration paths; application-independent verification quality; URL-only commercial implementation; dedicated inbox provisioning/self-signup; and reproducibility/generalization of maintainer benchmarks. These are limits, not claims of runtime defects.
