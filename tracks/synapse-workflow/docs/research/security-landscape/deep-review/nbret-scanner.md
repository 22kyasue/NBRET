# NBRET scanner workflow and evidence boundaries

2026-10-17; source hashes in `file-queue.json`. These files are uncommitted working-tree implementations, not falsely attributed to base commit `0fcdfa6`. ## Entry, lifecycle and execution

`tiers-cli.mjs:1–22` imports runners and parses CLI configuration; 23–32 reads JSON, applies output/analysis overrides and injects the environment API key for scanner configuration. 33–41 invokes the runner, emits compact status and sets failure exit codes. A `bounded` scan without errors is not among failure-status strings. The CLI is an interface, not proof of authorization.

`tiers.mjs:1–19` creates shared scope and wraps phase errors; 20–30 executes capture, an offline draft contract plan, exploration, explicit probes and optional scans. These are sequential phases; the draft is not automatically executed. 31–43 executes analysis/checks; 44–54 aggregates phase statuses and artifact links; 55–68 writes the human report, including alert counts and explicit limits. Full pipeline status is not a vulnerability verdict.

`managed-zap.mjs:1–19` reads a local installation receipt, validates its version string and resolves Java/install paths. This runtime path does not rehash the installed JAR/addons against the downloaded distribution. 20–28 allocates a private runtime directory, releases an ephemeral-port reservation and spawns one hidden Java child with random API key. There is a port release/start race; successful version/key access is the subsequent check, not atomic socket ownership. 29–39 stops only the child and closes its log; after SIGKILL it does not explicitly await a second exit event. 40–52 polls version/startup and cleans up on failure. 54–69 validates scope/mode and chooses explicit shared endpoint versus owned daemon; startup failures produce an artifact. 70–76 runs the scanner, labels daemon ownership and always requests daemon stop. That metadata is written before stop completes and does not itself prove process exit.

`setup-zap.mjs:1–16` fetches the latest release metadata and verifies archive bytes/size against its published digest; 17–26 saves/extracts into ignored storage and writes a receipt. It is version-pinned by the resulting receipt, not by a hardcoded release choice. Download integrity is not installed-runtime integrity or plugin inventory. This investigation did not rerun setup or replace installed files.

## `zap.mjs`, complete 1–106

| Lines | Meaningful operation and follow-up |
| --- | --- |
| 1–16 | Exact-origin scope, loopback-only API endpoint and explicit URL/budget validation. URL scope is selection configuration; no independent process/network firewall is established. |
| 17–34 | New output/evidence, unique context name, deadline and API wrapper. API requests use a header key; errors are deliberately normalized. Mutation success with a lost response remains an uncertain operation. |

## Reporting and evidence-file dependency

`diagnose.mjs:1–31` derives keyed observed HTTP/asset failures and CSP review candidates. 32–48 handles UI failures/auth observations and explicitly warns that captured rejections do not establish a role matrix. 49–79 adds performance/accessibility hypotheses with limitations. **80–95** projects scanner summaries into unconfirmed scanner findings with generic/specific remediation, using evidence file plus plugin ID rather than an exact alert/message pointer. **96–128** adds unexercised/collection gaps, sorts priorities and counts categories. Its deduplication key is rule plus sanitized target, so distinct same-rule/same-URL instances may collapse; confirm with a synthetic reporting case before calling this a runtime finding.

`evidence-files.mjs:1–12` resolves real paths, rejects escape/root equality, checks size before and after file read; 14–25 parses JSON and distinguishes missing from invalid optional files. Canonical path checks do not prove file identity stayed unchanged between `realpath`, `stat` and `readFile`; schema validation and trusted-origin assumptions are separate. It follows filesystem symlinks via realpath and reads only a contained resolved target under ordinary non-racing conditions. No hostile local race was tested.

## Tests read alongside implementation

`test/tiers.test.mjs:1–47` probes synthetic values/redaction/write rejection/redirect behavior. 49–70 uses a fake browser driver to test bounded exploration/owned-tab cleanup. **72–96** uses a fake ZAP transport to assert context ID, nonrecursive scope flags, history-wait behavior and omission of a synthetic evidence string. It does not execute the real scanner or verify all scope effects. 98–118 tests HTTP deadline and fake crawl bounds. **120–137** simulates a failure after receiving a scan ID and verifies stop/remove calls; it does not cover a lost start/context response. Existing focused tests therefore do not establish uncertain-mutation cleanup.

## New findings, carefully scoped

**SC-01: alert attribution exceeds selected path.** Source: 78–84. The [simulated-API receipt](scanner-adapter-lab-receipt.json) supplies `/allowed` URL scope but the adapter retains `/outside` on the same origin, while dropping a foreign-origin alert. It also drops proof/message/alert fields. This establishes adapter projection behavior, not that the real scanner generated an out-of-scope attack or that every managed run contains stale alerts. Next: verify real ZAP alert API selection and a passive-only owned-daemon fixture.

**SC-02: scan-start response loss leaves no stoppable ID.** Source: 61–63, 92–95. The simulation models side effect then response failure; adapter records failed and removes context but sends no stop. It neither retries nor globally stops unrelated scans, which avoids different hazards. Real daemon execution state after response loss remains untested; managed process ownership offers a stronger containment path than shared operation. Next: trace context deletion and scan ownership upstream.

**SC-03: context-create response loss skips removal.** Source: 46–47, 96–99. Simulation models context creation then loss; no removal follows because `contextId` never becomes defined. The name is already known but is not used for reconciliation. This is an uncertain context lifecycle, not proof of an exploit. No production repair applied.

**SC-04: shared passive queue affects completion.** Source: 72–77. The simulation keeps the queue nonempty and obtains timed-out status after approximately one second despite no owned active scan. Next: establish whether ZAP's count is global and whether a bounded per-message/operation completion criterion exists.

**SC-05: progress 100 does not imply full execution.** ZAP `ActiveScanAPI.java:973–981` returns 100 for a stopped scan. NBRET's numeric-only loop cannot distinguish that case. This is a cross-source semantic finding; no real interrupted scan has yet been exercised. Per-rule progress/states and omitted/failed rules need to be collected before stronger assurance claims.

These findings change proposed evidence design: retain stable run/context/scan/message/alert identities and actual policy/rule versions, distinguish requested/started/unknown/stopped/finished states, and never reconstruct validation proof from a summary count. These are research conclusions; fixing NBRET is a separate implementation action.
# Reporting continuation: complete source reads

**Synthetic reporting validation:** the [predeclared plan](report-state-lab-plan.md) and [receipt](report-state-lab-receipt.json) execute actual `runAnalysis` with coherent synthetic capture/explore/probe artifacts and failed scanner input. It retains scanner.status=failed in analysis JSON while emitting coverage=no-recorded-gaps. Neither rendered report includes SCAN_FAILED. Zero network/captured-code execution; source and artifact hashes preserved. This validates that combination, not every real failure or a claim that the caveats assert security assurance.

`src/analyze.mjs:1–22` defines deterministic formatting/count/role heuristics. **23–58** loads alternate capture/probe paths and optional external scan/access/reader inputs; it bounds top-level network arrays but does not bind separate input artifacts to one identity/environment/run. Explicit supplemental input is supported, so this is an attribution requirement rather than inherently invalid use. **59–89** computes inventories and saves dataset summaries from successful HTTP 200 JSON, labeling filename-derived roles inferred. **90–115** groups observed API rejections and derives an application-role hypothesis; the wording explicitly avoids claiming universal authorization. **116–131** records collection/exploration/probe gaps and copies scanner status/alerts/count directly. Scanner errors or missing scanner execution do not create a coverage gap here. Consequently `no-recorded-gaps` is narrower than complete testing and can coexist with a failed/missing scan. **132–154** optionally constructs static structure/workflows, records truncation/unavailable source gaps and recomputes coverage. **155–169** delegates diagnosis and emits fix guidance/evidence references. **170–189** emits resolved static workflows and module summaries with appropriate causality/coverage caveats. **190–213** emits JSON, HTML/reader report, suggested checks and Markdown. The Markdown lists scanner mode/count with a review caveat; it does not include scanner terminal status in that sentence. These are source observations; synthetic reporting propagation is a next lab, not yet runtime validated.

`src/report-html.mjs:1–9` escapes dynamic strings, renders static list/table helpers and selects resolved workflows. **10–26** renders route/access evidence, API observations and explicitly inferred architecture. **27–39** creates a standalone document with escaped dynamic fields, findings/diagnosis, workflow caveats, coverage gaps and provenance. Scanner findings appear through diagnosis with confirmation language, but scanner terminal status from `a.testing.scanner` is not rendered directly. Input reference display is not a cryptographic identity binding. No scripts or remote assets are included in this renderer. The separate reader-report renderer remains queued.
