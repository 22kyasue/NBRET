## Terminal outcome propagation into NBRET

Source chain: explicit stop sets Scanner.isStop → ActiveScan.isStopped true and getState FINISHED → ActiveScanAPI status returns 100 → `src/zap.mjs` exits its progress loop, clears pendingScan, drains the shared passive queue, fetches alert summaries and sets completed if not truncated. `src/tiers.mjs:46–68` accepts completed scanner status into aggregate completion and prints it in the report. Its final warning correctly limits security coverage, but does not restore interruption provenance. Engine exceptions are another source-level ambiguity: they are logged before unconditional completion notification. This does **not** demonstrate which particular failures can be triggered in a real daemon or that all worker failures follow the same path.

The predeclared [terminal adapter experiment](terminal-state-lab-plan.md) ran actual adapter code with an in-memory status=100 response and simulated interrupted ground truth. [Receipt](terminal-state-lab-receipt.json): completed, 11 API calls, no scanProgress/scans/message-ID/alert-ID request; zero network or Java execution. This is adapter runtime evidence, not a real interruption experiment. The separate ground truth is deliberately synthetic and not asserted to be known by the adapter.

Evidence that could improve interpretation includes an owned stop-request history, per-rule pending/running/completed/skipped states with reasons, request counts, configured policy/addon versions, actual engine/error logs and scan-linked message/alert IDs. None alone proves all intended tests succeeded: FINISHED and even COMPLETED events share the ambiguous terminal path. A real-daemon receipt is still needed to verify interruption timing, worker quiescence and specific exception behavior.
