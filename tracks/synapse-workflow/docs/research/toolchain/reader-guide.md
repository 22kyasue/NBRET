## Evidence labels for each assertion

| Label | Meaning in this dossier | Reader treatment |
| --- | --- | --- |
| Documented | Dated vendor/maintainer primary statement | Show source/date and edition; it is not a local run |
| Source-established | Behavior in fully inspected ranges at an exact pin | Link annotation and pin; retain caller/build conditions |
| Runtime-validated | Retained exact run with predefined oracle | Link plan, version, command, output, cleanup and limitations |
| Hypothesis / unresolved | Possible implication needing callers, dependency enforcement or a new oracle | Keep visibly open; never upgrade based on suspicious syntax alone |
| Narrowed / disproved | A proposed interpretation met contrary evidence | Keep original claim and the counterevidence together |
| Unavailable boundary | Proprietary internals, absent selected source, unknown customer state or unverified native build | Say exactly what is unavailable; continue accessible research |
| Stopped operation | User-directed stop on the flagged proposal | Show as stopped, not a failed runtime experiment; exact warning text is unavailable in this transcript |

For example: Nsock's IOCP copy-operation candidate has a direct source caller, but default Windows selection prefers poll. It is neither a proved fault in the shipped binary nor disproved for explicitly selected IOCP. Public Nsock undefines NDEBUG, which narrows the earlier concern about disabled assertions. The synchronous-callback documentation contradiction is source-established; effects on a particular caller remain separate. These distinctions are more useful than a single red/green vulnerability badge.
