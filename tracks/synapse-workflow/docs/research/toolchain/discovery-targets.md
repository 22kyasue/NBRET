# Discovery inputs, exclusion and DNS

Current continuation: this file remains canonical for expression expansion/exclusions/grouping. Its older next-read statements are historical: the [DNS implementation](dns-flow.md), [retry coordinator](discovery-timing.md), [port representation](discovery-packets.md), [Nsock lifecycle](nsock-flow.md) and [target/raw transport continuation](target-scan-flow.md) now close additional source paths. Their queues and native boundaries remain distinct.

Extends [discovery-packets.md](discovery-packets.md). Nmap commit `f06480daed9a9b2cdce61904222cc87788afdf84`. Three full files inspected; no resolution, scan, route change or live target run. A source snapshot is distinct from the dated stable release in the catalog.

`TargetGroup.cc` 1–205 complete. 84–95 destroys NetBlocks and rejects the last enumerated address. 100–146 parses expressions in batches bounded by ping_group_sz, delegates syntax to NetBlock, resolves accumulated DNS requests and replaces or removes unresolved blocks. 148–171 supports random generation and iterates/frees exhausted blocks; random public targeting was not used. 174–204 distinguishes the specifically resolved address from subnet-derived addresses and exposes original name/unscanned resolved addresses. A supplied hostname with a netmask can describe more than one approved endpoint; archive the expanded authorized set before any execution. NetBlock parsing remains the next dependency, not reviewed by this wrapper.

`nmap_dns.cc` 1–187 complete. 73–93 handles logging/progress. 95–124 configures a cached resolver with address family, callbacks and, in parallel mode, selected source/device/IP options/proxy chain/DNS servers. 128–158 initializes requests, checks parallel resolver availability, can fall back to system DNS, then invokes resolution and cleans progress state. Thus the earlier nsock service-proxy slice is not the only proxy-chain consumer at this pin: parallel DNS also receives the chain. This **does not** establish that all DNS/probes use it; resolver implementation and fallback need separate tracing. 161–180 requests PTR names for up hosts or always_resolve, then assigns returned names. PTR association is not authenticated host identity. The resolver implementation and OS name-service behavior remain unreviewed.

`targets.cc` 1–623 complete:

* 81–122 selects ARP/ND discovery for eligible local targets; lacking a MAC can classify a nonlocal target down, while localhost is treated up. 124–134 randomizes batch order or returns the last host. These are state policies, not literal statements emitted by the endpoint.
* 136–224 loads exclusions. File entries first try address syntax without DNS; unresolved names are resolved and optional netmasks reattached to each address. An unresolved excluded name causes fatal failure rather than silent omission in this path. String exclusions delegate to addrset with resolution allowed. addrset/name parsing is a separate dependency. Exclusions constrain addresses selected here; they do not supply engagement authorization.
* 234–267 reuses group timing estimates by device and delegates ping scanning. 269–316 divides raw-scan host groups when interface/source/directness/family differs or an IP duplicates another in the batch. This protects reply attribution, not every external sensor's attribution.
* 324–385 allocates host batches, buffers deferred targets, gets expressions from command/file input and, when enabled, consumes newly discovered NSE target expressions. Newly discovered addresses need explicit scope checks before an authorized assessment wrapper admits them. No script or automatic discovery was exercised.
* 389–450 creates a target, records resolved name/unscanned alternatives for the original resolved address, and for raw scans obtains route, next hop, source/interface and MTU. Route failure skips the target. The configured application proxy is not a guarantee of raw-scan routing.
* 452–520 enforces maximum selected count, enumerates expressions, rejects excluded addresses, handles resume position and optionally adds selected addresses to exclusion state for uniqueness. 523–591 fills compatible batches, optionally shuffles, checks Ethernet datalink capability (including a comment that some VPN interfaces only appear Ethernet-like), performs ARP/ND and resolves next-hop MACs as needed.
* 593–623 distinguishes disabled discovery/loopback from actual ping scanning, optionally reverse-resolves and returns targets. With discovery disabled, HOST_UP can be set with reason ER_USER; this is an operator assumption used to proceed, **not independent reachability evidence**. Preserve state reason in reports. Input/selected/skipped/discovered/observed counts answer different questions.

`libnetutil/NetBlock.cc` 1–752 complete. 64–120 defines IPv4 range, IPv6 netmask and hostname implementations. 122–214 splits netmask and parses each IPv4 octet into bit vectors, rejecting out-of-range/reversed/trailing syntax. 216–282 distinguishes numeric/ranged IPv4, numeric IPv6 and deferred hostname DNS; IPv4 prefix greater than 32 logs and assumes one host rather than uniformly rejecting it. 284–326 tracks resolved addresses and random IPv4 generation with reserved/excluded-address avoidance. None of that random generation ran. 328–447 enumerates IPv4 vectors and expands netmasks; 449–506 renders ranges and resets a single address. 508–625 enumerates IPv6 ranges, preserves/infer interface scope IDs and applies masks; 627–662 renders its prefix. 664–730 selects matching-address-family DNS answers, ordinarily the first unless resolve_all, retains unscanned alternatives, constructs the numeric block and applies the requested netmask. 734–750 prevents enumeration before hostname resolution and renders the hostname expression. This explains why hostname, chosen IP, all DNS answers and derived subnet are distinct scope/evidence records. Parsing an expression is not approval to contact its expansion; large IPv6 address spaces also require an external count/time budget. Netmask edge cases, duplicate DNS answers and resolve_all transitions need predefined offline tests before claiming exhaustiveness.

The input chain now connects expression source → parsed blocks/DNS → resolved/derived addresses → exclusions/resume/uniqueness → route-compatible batches → discovery policy → target → previously reviewed connect engine/state/reason → service deduction/output. Remaining dependencies: addrset parser, DNS resolver/transport, route helpers, outer retry/final-timeout scheduler, PortList state storage and nsock internals. The chain is not yet a complete command-to-report audit or a runtime validation.
