# VPNs, proxies and the path an assessment takes

Research synthesis, 2026-10-17. No routes, VPNs, DNS settings, tunnels or network agents were configured on this PC. The transport description does not supply permission to assess the destination.

| Mechanism | What it supplies / typical identity | Encryption and visibility boundary | Routing, DNS and assessment implications |
| --- | --- | --- | --- |
| Commercial VPN service | A tunnel to an operated egress service, commonly authenticated by subscription/device credentials. Usually intended to change the public network exit and protect the local segment. | Tunnel encryption ends at the provider endpoint. HTTPS can continue protecting app contents beyond it. The provider can observe relevant connection metadata and may have account/payment/IP records; the destination still sees application identity and the VPN exit. | Full/split routing, exceptions and DNS behavior depend on client/platform/config. It does not create access to a client's private environment or make a user anonymous. No particular provider's logging promises are verified here. |
| Organizational access VPN | A managed path from an authenticated user/device into selected organizational resources. Often includes device posture and MFA. | Encryption protects the configured tunnel segment; gateways and internal controls can log identity, routes and traffic metadata. Application TLS and application authorization remain separate. | Allowed subnets, split DNS, source NAT and firewall rules define reachability. Scope must name assets and actions separately. Connecting as a test user does not mean every reachable subnet is approved. |
| Mesh overlay, e.g. Tailscale | Private device-to-device addressing and policy plus coordination/NAT traversal. Identity includes enrolled device keys and access policy, not just an exit IP. | [Tailscale documents WireGuard-encrypted device traffic](https://tailscale.com/docs/concepts/tailscale-encryption); relay transport does not decrypt the inner packets. Coordination still needs metadata. This is a vendor architecture statement, not an independent privacy audit. | Default overlay traffic and public internet egress are different. [Exit nodes](https://tailscale.com/docs/features/exit-nodes) route internet-bound traffic when selected; subnet routers expose configured other networks. DNS policy and access policy are separate from routing. Do not presume ordinary public traffic traverses an overlay without checking configuration. |
| SOCKS proxy | Application-level relay for supported connections; SOCKS5 specifies negotiation and address/connection handling. Authentication is mechanism-dependent. | [RFC 1928](https://www.rfc-editor.org/rfc/rfc1928) is not a blanket encryption guarantee. A plain SOCKS connection does not itself provide TLS-like protection; another protected transport can carry it. The proxy knows relay destinations. | Only applications configured to use it participate. Name resolution may be local or proxy-side according to client/address usage. Raw probes and arbitrary OS traffic do not automatically pass through it. Hostname/IP scope checks must account for where resolution happens. |
| HTTP forward proxy / CONNECT | HTTP-aware intermediary; CONNECT can establish a tunnel. Proxy identity can differ from destination application identity. | A tunneling proxy ordinarily does not see tunneled TLS plaintext. An intercepting testing proxy terminates/reissues TLS when the test client trusts it, giving that proxy access to credentials/content. Certificate trust is a security boundary. | Proxy exclusions, PAC rules, browser-only settings and protocols can bypass it. Proxy logs show only traffic traversing it. Scope should be checked at actual destination selection, not inferred from a URL shown in an earlier UI. |
| SSH tunnel | Selected forwarded connection paths within an authenticated SSH connection. The SSH server key identifies the server; user keys/passwords authenticate the login. | [OpenSSH ssh manual](https://man.openbsd.org/ssh.1) documents forwarding within the secure channel. Protection ends at the SSH peer for forwarded plain application traffic; the next leg needs its own protection if required. | Selected local/remote/dynamic forwards are not automatically a whole-device VPN. DNS and destination resolution depend on forwarding type/client. Server policy and listener binding constrain access. A tunnel changes vantage point and logging attribution; it does not grant wider test scope. |
| Assessment jump host | A controlled machine from which permitted tools run, with agreed accounts, logs and network access. It is a host/operating model, not one encryption protocol. | Security depends on access control, patching, evidence storage, session logging and the protocols used. It may see plaintext and credentials in its own processes. | Its source IP and routes become the assessment vantage point. Firewall/egress rules can enforce a boundary outside tools. Preserve operator attribution and avoid shared ambient credentials. A jump host can be a lab component without becoming covert infrastructure. |
| Isolated lab network | A deliberate topology for owned synthetic fixtures; separation is enforced by virtual/physical network and host controls. | “Private IP” alone does not establish isolation. Shared mounts, management interfaces, DNS and outbound internet can bridge boundaries. | Define permitted destinations, DNS, egress, management access, resource budgets and cleanup before running risky capabilities. This study has not created such a network. |

## What to inspect before interpreting results

Record where the process runs; resolved destination and address family; chosen interface/route; DNS resolver/search suffix; proxy exceptions; tunnel endpoints; source NAT; trust roots; actor and device identity; firewall decisions; and the collection time. A request can use a private DNS answer while packets leave through an unexpected route. An IPv4-only rule can miss IPv6. Split tunneling can protect one subnet while another request leaves directly. Application libraries can ignore desktop proxy settings. These are testable failure hypotheses, not findings about this PC.

Packet capture before encryption sees different data from capture after encryption. A VPN operator, corporate gateway, jump-host administrator and application server have different visibility. HTTPS authentication, VPN membership and a scope authorization document answer different questions. Public IP changes do not erase browser sessions, API credentials, device signals or service logs.

## Appropriate role during an assessment

Use connectivity to obtain the **agreed vantage point**, preserve attribution and reproduce the client's network assumptions. Keep source addresses, accounts and timelines in the engagement record so defenders can correlate activity. Diagnose denied reachability separately from failed authentication and failed authorization. The first says the path did not succeed; the second says an identity was not accepted; the third says an accepted identity lacked an action. A timeout alone cannot reliably choose between them.

The commercial/organizational descriptions above are class-level analysis, not claims that every vendor behaves identically. Product-specific route, DNS, key lifecycle, logging, licensing and enterprise controls require separate versioned verification. No anonymity, absence of logs, or authorization claim follows from the word “VPN.”

## Destination caches and changing policy

Tomo's [guarded loopback dependency experiment](../security-landscape/deep-review/nuclei-dialer-cache-lab.md), dated 2026-10-17, exercises Fastdialer 0.5.25 with NetworkPolicy 0.1.54 under the selected Nuclei dependency graph. Two runs each passed 12 predefined assertions: reusing the same network/address cache retained an earlier context-selected IP and skipped a changed validation callback; fresh dialers honored the new IP and a denied validation decision. The DNS trap received zero queries. These are Tomo's execution receipts, not an additional experiment performed for this toolchain study.

The integration question is whether cached destination authority lives longer than the policy or context that justified it. A configuration change alone does not establish that existing cached state was revalidated. Evaluate cache lifetime, invalidation and destination checks together when interpreting an assessment tool's scope controls. The [native-network review](../security-landscape/deep-review/nuclei-native-network.md) distinguishes this component behavior from Nuclei initialization: that initialization does not install the tested callback. This experiment therefore does not establish a full-engine Nuclei scope escape. Scheme/port concerns remain source observations without runtime validation.
