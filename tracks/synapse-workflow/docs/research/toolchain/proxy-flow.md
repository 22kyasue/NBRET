## Listener manager and hook bridge

* 44–110 serializes mode updates under a lock, retains matching instances, stops removed modes before starting new modes, and records errors from gather. Startup success is a manager result, not a traffic observation.
* 113–223 tracks active connections in a finally-protected registration context; defines streamed-body storage default **false**, connection strategy default **eager**, streaming threshold and body-size limit default **None**, host-header rewriting and inbound validation default **true**. An unset body limit is not a resource budget.
* 225–310 parses configured limits, validates source IP and mode syntax, rejects duplicate listen tuples, handles platform support for transparent mode, and starts mode updates. These validate proxy configuration; they do not enforce an engagement's asset allowlist.
* 312–375 handles injection only for known live flows and compatible protocols, scheduling events into an existing connection.
* 376–397 sets upstream source address when unset and prevents simple self-connections to known listener address/port combinations. This specific recursion guard is not a general DNS-resolved destination policy.

`mitmproxy/proxy/mode_servers.py` **1–210 inspected, remainder unread**: 61–75 connects the network handler to `master.addons.handle_lifecycle`, then waits for intercepted flow resume. The inactivity watchdog is deliberately disarmed around the hook and wait. Thus the connection inactivity timeout does not supply a deadline for an indefinitely waiting addon/interception. 91–183 defines typed mode factories and start/stop error tracking. 185–210 constructs handlers and begins transparent-original-destination handling. Listener implementation and remaining modes must be traced before claiming listener/whole-process cleanup coverage.

* 465–499 builds client context and a simpler hook implementation. 502–611 is a standalone demonstration including explicitly insecure TLS callbacks. Those demonstration callbacks are **not** the production TLS configuration and were not run.

## HTTP message and extension flow

`mitmproxy/proxy/layers/http/__init__.py` 1–1211, complete:

* 1–158 imports protocol-specific parsers and defines modes, request validation and connection commands. Request scheme and configured inbound headers are checked; a destination tuple also carries TLS, upstream proxy and transport protocol for connection matching.
* 159–295 starts per-stream request/response buffers/states, constructs or adopts an HTTPFlow, validates early, branches CONNECT, resolves authority/transparent destination, normalizes regular HTTP/1 target and reverse Host header, checks limits, yields requestheaders and processes expectation/streaming. Flow mutation is part of proxy semantics, not a transparent copy of client intent.
* 296–361 streaming sends headers/body before the final request hook; optional stream callbacks transform chunks. With stored bodies enabled, **transformed** chunks are retained. Request hook at stream end cannot retroactively retract already forwarded bytes.
* 362–410 buffered request handling accumulates body, invokes request hook, checks kill, accepts an addon-supplied synthetic response or establishes an upstream connection and sends the possibly modified request. A response can therefore exist with no target application response.
* 412–493 response handling validates, runs responseheaders, then streams or buffers. With streaming and storage disabled, final flow content does not contain the forwarded body. Missing body content is not evidence an upstream response was empty.
* 494–567 invokes response hook, checks killed state, sends buffered body/trailers, transitions to WebSocket/raw TCP after 101 if enabled, drops ordinary streams and sends final end-of-message. In streaming mode, response hook runs after forwarded chunks.
* 568–650 obtains expected/buffered sizes; body limit violation produces an error hook and protocol error, sets errored/live state, and can close the upstream side. Streaming threshold changes processing/storage rather than rejecting traffic. Retaining streamed bodies can reintroduce memory cost.
* 652–755 validates headers (when enabled), emits explicit errors, detects kill and remote error while hooks were paused, distinguishes completed response from errors and drops failed streams. Do not relabel proxy-generated size/validation errors as application failures.
* 757–845 selects upstream based on the **post-hook** request host/port/scheme and connection settings; CONNECT has regular/upstream handling, eager/lazy behavior and separate connected/error hooks. A successful CONNECT response is not an application authorization verdict.
* 847–918 translates tunneled events and close semantics; errored states consume further events. 921–1065 maps connection events → HTTP events → per-stream commands → transport commands and routes completion events back to originating streams.
* 1067–1188 reuses matching connected peers, carries errors, stacks upstream proxy/TLS/QUIC/HTTP clients for new peers, and handles HTTP/2-to-HTTP/1 multiplexing constraints. 1191–1211 picks HTTP client by ALPN after connection establishment. The concrete HTTP/1 parser, TLS certificate verification, HTTP/2/3 and native Rust I/O internals remain separate dependency boundaries.

## HTTP/1 parser, message framing and bounded resource probe

`proxy/layers/http/_http1.py` 1–503 complete: 1–86 binds HTTP/1 state to a receive buffer and h11 body readers; 88–170 translates body/EOF/protocol events and waits before parsing another message. 171–220 closes/reuses based on EOF/Connection/protocol-conversion conditions. 223–337 handles server-side response serialization and request-header parse, then body-reader selection. 339–462 handles client-side request serialization, HTTP/2/3-to-HTTP/1 normalization (including cookies), response-header parse and peer closure. 465–503 selects tunnel/body reader and creates proxy error responses. Header parsing waits for a complete header block and explicitly leaves a header-size-DoS FIXME on both directions. That validates **body limit is not an incomplete-header-buffer cap at this parser layer**, with a finite small input; it does not establish whole-process exhaustion or bypass of independently configured deployment controls. No sockets or large/unbounded load were used.

### Serialization, HAR and configuration closure

Additional complete files at the same pin: `mitmproxy/coretypes/serializable.py` 1–200 and its tests 1–203; `mitmproxy/connection.py` 1–360 and tests 1–95; `mitmproxy/io/har.py` 1–160 and tests 1–65; `mitmproxy/addons/savehar.py` 1–313 and tests 1–263; `mitmproxy/optmanager.py` 1–638 and tests 1–520; script tests 1–341 and master tests 1–34. Source inspection only in this continuation.

Serialization consumes caller state dictionaries. Dataclass fields marked `serialize=False` are excluded; connection socket state is one such field. Reconstruction cannot establish a live socket merely by loading a recorded connection. Nested serializable objects may be updated in place; immutable children are replaced. Type/literal/container checks reject many invalid representations, but address tuples use a special zip with at most four slots. This is structured reconstruction, not authentication of evidence provenance or a universal schema validator. Connection identity is its UUID, independent of socket identity; copy creates a new UUID. TLS intent (`tls`), completed TLS timestamp, requested destination (`address`), resolved peer (`peername`) and intermediate proxy (`via`) are different facts. Address/via changes on an OPEN connection are explicitly rejected; the reviewed tests cover destination mutation and no-op assignment.

HAR export retains selected HTTP flow references until the `done` hook when hardump is enabled; it does not impose a memory budget in this file. Disabling hardump clears the retained list. Output constructs the full JSON byte string, optionally compresses it for `.zhar`, then writes directly to the selected path. There is no atomic rename/fsync transaction in this implementation. Non-HTTP flows are skipped. WebSocket flows wait until websocket_end. Response/error hook selection and later mutation can affect the referenced objects; this is not an immutable snapshot at collection. Connection timing is recorded once per UUID-equivalent server; missing durations become zero or -1. A response without a body and an unavailable/streamed body can share empty-content presentation; compare native state and streaming configuration before claiming body absence. Cookie expiry is deliberately omitted, though raw headers remain exported. Binary response content uses base64; request postData is emitted only for POST/PUT/PATCH, as text plus form parameters. No credential redaction appears here: headers, cookies, query strings and bodies need a separate evidence handling policy.

HAR import synthesizes client loopback addresses and chooses server port 80 for an `http://` URL, otherwise 443, independently of an explicit URL port. Request URL parsing still supplies the request's own authority, so imported connection metadata can diverge from request metadata. It reconstructs a response even for the export's status-0 error representation without restoring its `_error` field. Request/response timestamps use the same aggregate HAR interval; protocol versions outside the enumerated HTTP2/3 strings fall back to HTTP/1.1. Response content is decoded/re-encoded and finally both messages are decoded, deliberately changing compressed bytes. WebSocket message restoration is absent. Consequently HAR interchange is a useful view/replay input, not a lossless native-flow round trip or proof of the original connection path. Import fixture tests compare through web JSON using zip without an independent list-length assertion; they do not establish arbitrary HAR round-trip fidelity. These are source-established transformations, not a newly run corruption experiment.

Option values/defaults are deep copied on read. Known updates snapshot the options dictionary and invoke synchronous listeners; only `OptionsError` invokes the rollback path, which emits the error signal, restores the dictionary and sends another changed signal. It does not reverse arbitrary subscriber I/O or process state. Upstream tests explicitly observe both attempted and restored values. `update` applies known options before raising for remaining unknown keys; it is not a blanket all-input atomic transaction. Unknown configuration keys can instead be deferred until addon registration. The choices list is passed to argparse but `_Option.set` itself only calls type checking, so choice enforcement for other setters requires caller/addon review. Safe YAML loading avoids arbitrary YAML object construction, but non-mapping data shape handling must be followed through CLI error handlers. Config save opens the destination in write mode before serialization; this is not a durability guarantee for invalid configuration or interrupted writes.

Script tests specify logging of load/configure errors, reload on file changes, removal when a script disappears, duplicate rejection and configured addon order. They do not test the previously observed sys.path alias restoration boundary. One test modifies a source fixture directory, so executing the whole test file in place would require an isolated copy. Master's small test verifies logging an unhandled task exception and then explicit shutdown; it does not prove shutdown automatically follows every background failure. Remaining caller questions: error signal failures before rollback, addon side-effect recovery, failure during done/export and startup/CLI containment. No shutdown or persistence claim is promoted beyond these inspected paths.

Caller follow-up: `mitmproxy/addons/errorcheck.py` 1–56, `utils/signals.py` 1–138, `utils/typecheck.py` 1–73 and errorcheck/signal tests 1–44/1–80 are now complete. Reinspection of already-complete master/main/script identifies contrary evidence to a blanket "addon errors never stop startup" interpretation: ERROR logs during startup are accumulated by ErrorCheck, checked at several initialization boundaries, and can cause exit 1. After successful startup, `finish` removes that logger, so it is not a continuing fail-closed request policy. Master invokes done in a finally covering running/wait, but startup returns/errors before that try block have a distinct cleanup path. Script reload removes the previous namespace before attempting the replacement; a failed load does not restore the old addon here. Its watcher checks increasing mtime, so decreasing/unchanged timestamps are not a reload signal. Script.done requests cancellation without awaiting completion. These are source paths requiring lifecycle context, not a new runtime failure result.

Signals dispatch synchronously in receiver order without catching receiver exceptions. This confirms the narrower rollback concern: an exception from an errored subscriber can interrupt the rollback before the option dictionary restoration; a failure in the second changed notification occurs after restoration. The type helper checks option types without choices membership. CLI configuration catches OptionsError specifically; arbitrary non-mapping YAML shape errors are not converted by this catch. None of this establishes remote input control, a product-wide exploit or data loss on this PC. These questions are limited to trusted configuration/addon integration and evidence persistence behavior.

### Executed ordinary HAR interchange oracle

The independent [HAR plan](har-roundtrip-plan.md), [case receipt](har-roundtrip-receipt.json) and [process receipt](har-roundtrip-process.json) now validate the selected adapter transformations with native HTTPFlow objects and no requests.
