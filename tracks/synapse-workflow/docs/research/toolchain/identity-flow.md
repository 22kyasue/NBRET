## Collector entry, credentials and reproducibility

`src/Sharphound.cs` 1–269 complete:

* 17–70 enters Main, logs versions, checks the .NET runtime through registry, configures case-insensitive parsing and resolves collection methods. A startup compatibility message is a program string, not a verified compatibility matrix for newer analyzer releases.
* 72–108 translates options into flags and LDAP configuration. Negotiated authentication is specified; disabling signing, forcing SSL and disabling certificate verification are configurable. Merely naming LDAP does not establish secure transport—retain actual options and negotiated state. These settings were not exercised.
* 110–156 validates paired LDAP and local session-enumeration credential options. Credential strings are copied into configuration/context; this file does not implement a secret vault, automatic command-line redaction or memory zeroization. No existing credentials on this PC were inspected.
* 158–197 optionally creates metric sinks/timer, starts collection and logs outer exceptions. Outer error handling does not explicitly set a nonzero exit code here; downstream fault/return semantics need independent checking before interpreting process exit as completeness.
* 199–259 constructs a disposable BaseContext with search base, filters, domains, threads, throttling/timeouts, loop parameters, credentials and output settings; constructs cancellation source, then runs initialization/connection/domain/collection/loop/cache/finalization chain. The Console.CancelKeyPress handler is commented out in this entry point. This does not establish absence of all cancellation; follow the context/chain implementation.
* 261–269 exposes a synchronous PowerShell-facing wrapper around Main. It was not invoked.

`Sharphound.csproj` 1–89 complete: targets net472; assembly version 2.17.1. `CommonLibsVersion=4.9.1` and default `CommonSource=Dev` derive **4.9.2-dev***, which selects NuGet package versions via a wildcard for SharpHoundCommon and SharpHoundRPC. Stable and local-library modes are alternatives. Consequently this source commit alone does not pin executable dependency bytes. Require the actual resolved package versions/hashes and build settings for a reproducibility claim. Project also references CommandLineParser, channels, JSON and ZIP libraries. The build includes a Windows-only PowerShell packaging target; no collector build was executed.

Per-object processing errors continue; the dataset count is not an expected-total oracle. Processor/common-library internals are queued.

`src/Runtime/OutputWriter.cs` 1–248 complete: 19–75 constructs per-type writers and status timers; 77–105 reports processed count, rates and process memory (observability, not an enforced cap). 107–170 consumes channel items and routes by output type; unrecognized types throw. 172–193 sequentially flushes writers, stops/disposes status timer and calls ZipFiles. 195–248 returns null when output/ZIP disabled; otherwise creates archive, optionally sets password, copies each existing JSON into a named ZIP entry and deletes that JSON after closing its entry. ## Upload is a separate trust boundary

`cmd/api/src/api/v2/fileingest.go` 1–246 complete:

* 50–116 handles job listing with allowed sort/filter fields and pagination. Query parser internals remain queued. The direct `column[0]` access is a candidate empty-sort-input edge case; middleware/query normalization must be checked before calling it a reachable bug.
* 118–129 obtains a user from authentication context before creating a job. The entire route/middleware/role chain is not in this file; no conclusion about endpoint authorization follows from this callback alone.
* 131–188 checks content type, parses job ID, requires a running job, resolves file storage, saves/validates input, creates an ingest task and updates last-ingest. A failed task creation triggers file cleanup with a separate 30-second context. Successful response is **202 Accepted**, not proof that graph conversion/analysis has succeeded. Job owner/tenant restrictions must be traced in route and service/database layers.
* 190–246 supplies original-name fallback, job end transition, accepted-type listing and completion-task listing. The provided name is descriptive metadata; do not assume it is the actual temporary storage path.

`cmd/api/src/services/upload/upload.go` 1–193 complete:

* 46–83 classifies JSON/ZIP and sets diagnostic/error reporting. 85–118 creates a pipe, closes the pipe and source when context is canceled, validates in a goroutine while storage consumes the pipe, then waits for the buffered validation-result channel.
* 120–140 distinguishes cancellation, backend write error and validation error; invalid uploads invoke temp cleanup. 143–159 cleanup detaches cancellation but adds a 30-second deadline. Cleanup failures are logged; absence of leftovers is not established without a test/storage inspection.
* 161–187 ZIP is tee-written through ValidateZipFile. JSON is normalized to UTF-8, tee-written and passed to payload validator/schema. ZIP JSON validation is deferred to ingestion in graphify; upload acceptance alone therefore cannot establish every member's schema validity. Limits/ZIP-bomb protections and schema semantics require the validators themselves.

## From input metadata to graph operations

`packages/go/chow/ingest/ingest.go` 1–158 complete defines accepted original data-type names, original type/method/version metadata and method bit flags. `CollectionMethod.IsValid` (137–145) returns true if **any** known method flag is present; it does not require unknown bits to be zero. That is a narrow type-helper fact, not a vulnerability finding. Validation caller behavior remains queued.

`cmd/api/src/services/graphify/ingest.go` 1–457 complete:

* 42–155 defines batch, deduplication manager, endpoint resolver, stats and options. A single IngestTime is used for entities' lastseen within an ingest run; a zero value becomes now. **Ingest freshness is not necessarily source-observation freshness.** Old uploaded data can be newly ingested; collection timestamps/provenance need separate retention.
* 157–187 defines ChangeManager's deduplication/async submission and batch update interfaces. Deduplication does not establish truth or current validity of a relationship.
* 189–224 ZIP members are fully parsed/validated here; non-ZIP data parses metadata because upload has already validated it. Reader rewinds before dispatch. This is a trust assumption between upload and ingest stages; independent ingest sources must be checked for equivalent validation.
* 226–315 dispatches by payload type; missing handlers return an error; source kinds may be registered; node and relationship writes collect errors rather than supplying an all-or-nothing proof in this layer. Transaction/rollback semantics belong to batch/database callers.
* 317–347 adds group distinguished-name relationships and Azure data handling. 350–413 maps input types to decoders/converters; computers require metadata version >=5 here. 415–457 handles generic node/edge arrays, optional source metadata and decoder selection.

`cmd/api/src/api/tools/ingest.go` 1–237 complete is an **operator evidence-retention control**, not the normal upload path. 39–69 stores retention config. 72–103 normalizes retained archive entry names and streams files into tar with mode 0600; 105–164 locks retention reads and streams gzip/tar results. 166–237 enables retention or disables it and asynchronously attempts cleanup with a detached five-minute context. The code explicitly describes cleanup as best effort. The final HTTP status is written after streaming has begun; failure after some output is a partial-artifact hypothesis to test, not a proven exploitable endpoint issue. Auth middleware/storage implementations remain unread.

## What the graph can and cannot establish

Collected permission attributes → converted relationship → stored edge → graph path → controlled capability test are different evidence states. Schema validity establishes a document shape/type constraint, not truthful collection. A new lastseen is not necessarily a new observation. A path has edge-specific preconditions and may depend on transient sessions, unreachable systems or unavailable privileges. A graph result does not carry permission to exercise the path.

Next required slice: resolve collector default dependency bytes; extend object processing and group conversion into endpoint resolution; inspect actual database transaction and reconciliation/deletion implementation; trace a specific query/analysis rule and its edge predicates. Test stale/missing/denied observations with synthetic datasets and predefined oracles. Agate owns a distinct authorization-evaluator study; reuse that comparison without duplicating ownership. The unit lab below covers mocked ingestion decisions; collection and database integration remain untested.

## Actual dependency: BatchOperation is not a whole-ingest atomicity promise

The next dependency review pins **the actual Go test dependency** dawgs v0.9.2 at module-origin commit `d0640cfb421e2b9f4fc249de733c3d6e52f1a57f`. Go module origin/zip content sum is retained in snapshots.json; an h1 module content sum is not the raw ZIP SHA-256 or a release signature. No database integration was run.

`drivers/neo4j/driver.go` 1–199 complete: 50–83 acquires a concurrency slot, creates session/batch, invokes callback, returns callback error directly or calls batch.Commit; defers Close. Other methods supply transaction/query/schema helpers; SetDefaultGraph explicitly does not emulate isolated graph namespaces in this driver. This driver behavior is not a claim about tenant isolation in a deployed BloodHound service.

`drivers/neo4j/batch.go` 1–374 complete: 32–110 creates nodes grouped by kinds with ordinal checks; 144–170 buffers node/edge upserts, flushing at the batch threshold. A nil update return may mean only in-memory buffering. 180–218 flushes remaining buffers before inner commit; 220–265 closes/delegates operations; 272–361 builds/flushes groups and deletion/update buffers; 364–374 constructs buffers and inner transaction.

`drivers/neo4j/transaction.go` 1–467 complete: 20–25 defaults batch-write size 20,000, flush size five times that, concurrent slots 50 (deployment may override). 60–132 builds chunked node/edge updates and accounts writes. **145–178 commits and clears inner transaction when write count reaches flush size**; currentTx lazily begins the next one. 181–190 executes/accounting; 193–295 constructs node/edge query operations. 298–346 executes raw queries and optionally logs selected parameters when query-analysis mode is enabled; evidence/permission data can therefore enter diagnostic logs. 368–388 commits/closes only the current inner transaction. Later callback failure cannot roll back an already committed prior chunk. That is source-established control flow plus ordinary transaction semantics, not an observed customer data-loss incident.

PostgreSQL source is **partial**, with ranges kept exact: `drivers/pg/driver.go` 1–180 shows BatchOperation callback/commit (95–123) and comments that write-flush rotation option is a no-op (91–93). `drivers/pg/batch.go` 1–190, 405–485, 651–706 and 800–881 inspected: newBatch calls newTransactionWrapper with **allocateTransaction=false**; upsert buffers flush to `innerTransaction.conn.Query` for nodes (405–438) and `conn.Exec` for edges (651–672). Commit flushes remaining buffers then calls wrapper.Commit. Some bulk methods allocate/commit their own local transaction. `drivers/pg/transaction.go` 1–307 complete: wrapper allocates a transaction only if requested, otherwise routes to connection; Close/Commit only roll back/commit when wrapper.tx is non-nil. Consequently the reviewed batch path is not one enclosing SQL transaction either. Other PG bulk paths/query builders remain unread; do not extrapolate every operation from these slices.

**Practical inference:** ingest failure may coexist with persisted earlier entities; “written” may count buffered accepted operations before persistence; “processed” also includes deduplicated operations. Reports/retests should retain the selected driver, configuration, file-level errors/UserDataErrs, task state and an independent resulting graph check. To validate recovery/atomicity, a future isolated database lab needs a seeded baseline, enough records to cross an explicit low test threshold, injected later failure, exact post-run node/edge oracle and cleanup. That experiment has not run. Never describe Graphify's comment about rollback as a verified whole-file transaction guarantee.
