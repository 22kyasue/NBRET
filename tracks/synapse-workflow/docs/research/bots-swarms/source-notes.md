## rate-limiter-flexible: quota authority is the chosen key and storage scope

Pin `d19a457455338b73172d47d004f402bd0b748152`. Fully read `lib/RateLimiterMemory.js` (1–199), `RateLimiterAbstract.js` (1–142), `RateLimiterRes.js` (1–65), `component/MemoryStorage/MemoryStorage.js` (1–131), and `Record.js` (1–42).

`RateLimiterAbstract.js` 13–43 initializes and validates finite point/duration configuration; 50–83 sets blocking/even-spacing defaults; 86–111 namespaces the caller key and selects duration. It does not authenticate that key or derive it from an account. `RateLimiterMemory.js` 1–10 creates a **new storage object per limiter instance**. Lines 18–46 synchronously increment that key, compute remaining points, reject when consumed exceeds the configured budget, optionally set a block interval, or delay a permitted resolution for even spacing. This is a fixed-window count mechanism, not a continuously refilling token bucket. Lines 48–104 expose penalty/reward/block/set/get/delete; these are privileged application controls, not public HTTP policy. Lines 106–199 dump and restore records with schema/expiry checks; that is not a tamper-proof persisted quota authority.

`MemoryStorage.js` 4–28 owns a local Map and uses lazy expiry checks in `incrby`; 31–55 replaces the record, clears old timers, installs a new expiry and an unreferenced deletion timer. Lines 62–71 return stored values and remaining time; unlike `incrby`, `get` does not itself reject a logically expired record before timer cleanup. Lines 78–88 delete and clear timers; 96–129 validate and restore expiry. `Record.js` 8–31 stores parsed integer values and normalized expiry; `RateLimiterRes.js` is the returned data/serialization object. A rejection has to be caught by the application and converted to denial **before** protected work. The library does not write HTTP 429 itself.

Complete test reading: `test/RateLimiterMemory.test.js` 1–521 contains count, excess-consumption and even-spacing tests (1–177), penalty/reward/prefix tests (178–224), block interval behavior (226–293), lookup/delete (295–349), custom/zero duration and explicit set (351–479), lazy expiry reset (481–505) and zero-budget rejection (507–521). These tests were read but not run with their Mocha/Chai harness. Our [lab](lab.mjs) imports the exact pinned implementation directly, catches rejection before producing tenant data, and observes the deployment/key-selection outcomes recorded in [the receipt](lab-receipt-1792266832801.json). Redis/cluster backends and distributed failure behavior remain unread/unexecuted; do not extrapolate local Map behavior to them.

## Scrapy: account separation is a maintained jar mapping

Pin `32579047288e06656d10b7fe97fc9acb092de8ad`. Fully read `scrapy/downloadermiddlewares/cookies.py` 1–162. Lines 1–35 import cookie/request helpers and public-suffix domain extraction; 37–52 create a mapping of jars and respect enabled/debug configuration. Lines 54–71 filter cookies through domain/public-suffix and underlying jar checks. Lines 73–89 select `request.meta.get("cookiejar")`, merge request cookies, remove a preexisting Cookie header and regenerate it from that selected jar. Missing keys select the shared `None` entry. Lines 91–106 use the same selector to store response cookies. Lines 108–130 can log cookie values when debug is enabled; avoid enabling this with sensitive sessions. Lines 132–162 format explicit cookie values, flags and secure defaults through helpers.

Partial tests `tests/test_downloadermiddleware_cookies.py` 480–630 show bypass-merge behavior (496–523), cookie path/domain cases (525–568), same-jar carryover (570–584) and separate `store1`/`store2` histories with deliberately copied response metadata (586–621). No Scrapy runtime/session test has run. The default-jar observation is a configuration hazard to test, not a claim of a Scrapy vulnerability.

Continuation: completely read `scrapy/http/cookies.py` 1–208. Completely read `retry.py` 1–201: 93–120 increments bounded retry metadata and uses request.copy(), preserving existing metadata while setting a one-time duplicate-filter exception and adjusted priority; 121–136 records exhaustion; 139–201 selects configured statuses/exceptions and `dont_retry`. Completely read `redirect.py` 1–268: 88–118 bounds redirect count; 120–175 replaces a request, removes certain cross-origin credential headers, and handles referer; 177–234 changes methods for applicable redirect statuses; 237–268 handles meta-refresh. A redirect's Authorization header is removed on scheme/host/port changes (166–171). Cookie-header handling uses different conditions (159–163) and later cookie middleware can regenerate it from jar policy.

Completely read `scrapy/http/request/__init__.py` 1–527: attributes include meta (131–149); constructor shallow-copies it (168–192); copy delegates to replace, which carries attributes into a new constructor (399–429). Therefore retry/redirect replacement preserves the jar selector unless explicitly overridden, while nested mutable metadata values can remain shared. Serialization includes headers and other attributes (483–510), so persisted request dumps need credential handling. This establishes the selected construction chain statically; middleware order, helper details and full test execution remain gaps.

## BullMQ: lease ownership and recovery are separate from effect ownership

This is an internal protocol convention, not an access-control boundary against a caller with Redis access; token creation and caller permissions still need tracing.

`moveStalledJobsToWait-9.lua` 23–51 loads helpers and suppresses overlapping checks with an expiring check key; 53–75 traverses previously marked candidates, requires a missing job lock and removes an active entry before incrementing stall count. ## Coraza: classification must reach the HTTP connector

Pin `b3c652296752293652db04a54079c020e1be3c01`. Coraza is a WAF rule engine, included as a representative rejection/enforcement implementation. It is not inherently a behavioral bot classifier and no bot-detection accuracy is claimed.

Fully read `http/middleware.go` 1–174: 26–62 populates connection/URI/headers, including promoted Host and Transfer-Encoding; 64–97 returns early on request phase interruption and restores body readability when buffering was required. Lines 100–115 return the original handler for nil WAF or select a transaction constructor. Lines 117–126 defer logging and transaction close. Lines 128–145 directly invoke the application if the rule engine is off; otherwise return on request-processing error or write interruption status before invoking application code. Lines 147–158 wrap and process the response around the downstream handler. Lines 161–173 choose 403 for a deny action lacking a status, otherwise the provided status or supplied default.

The error branch 139–141 logs and returns without explicitly writing an error status. **Source-established:** the protected handler is not invoked through this branch. **Inference requiring a runtime oracle:** a Go HTTP response with no status/body written could appear as an empty default success response. Do not equate a response status alone with handler execution or successful denial; no Go runtime is available on PATH in this session, so this has not been executed.

Partial `internal/corazawaf/transaction.go` 330–375 shows `Interrupt` storing the active interruption only when engine is On, while DetectionOnly stores a separate would-interrupt observation. Partial 922–960 shows request-header processing returning nil when off and returning the actual interruption after rule evaluation; the body-limit helper constructs a denial separately. This is a boundary map, not a complete review of all detection-only/body-limit interactions.

Completely read `http/middleware_test.go` 1–678: request/transfer-encoding cases (30–135), chained rule test (174–238), HTTP fixture definition and request/response rejection cases (255–404), off-mode cases (406–454), real httptest connector harness (456–550), status mapping including a deny with configured 202 (552–586), nil WAF (588–594), and handler API cases (596–678). Partial-body processing deliberately inspects a prefix while passing the complete body to the application (303–313): a configured inspection budget is not full-payload coverage. Test labels such as true positive do not establish bot-classifier accuracy. Full interceptor/response paths remain queued. No Coraza tests were executed.

Response continuation: complete `http/interceptor.go` 1–298 read. Header interception (50–86) evaluates response headers and flushes denial status; body writes (113–161) buffer inspectable data or directly forward inaccessible/unprocessable data; Flush (172–186) is constrained by whether buffering permits it. Buffered release (188–211) flushes status before body copy. wrap (227–298) preserves optional HTTP interfaces, skips final body work after hijack or interruption, and processes/buffers the response after the handler. **Ordering finding:** response-phase rejection can suppress disclosure, but downstream application code has already run; it cannot be treated as prevention or rollback of its side effects. WebSocket payload coverage and body-engine behavior require their own review. No Go execution or behavioral bot-classifier measurement is implied.

## memberlist: peer suspicion is fallible coordination state

Pin `5cd2c4b0fb09caea5de03aae1adb9c36374ef3e0`, added after the initial four repositories with 40 Go implementation/test files initially unread. Complete `suspicion.go` 1–134 stores confirmations, starts a bounded timer and excludes the initiating reporter (12–82); it calculates decreasing timeout with more reports (85–100); Confirm (102–133) deduplicates by reporter name and adjusts/fires the timer. This is not cryptographic proof that named reporters are independent operators.

Complete `suspicion_test.go` 1–202 checks the timeout formula, duplicate report suppression, minimum timing, zero-confirmation expectations and immediate expiry; those tests were read, not run. Complete `awareness.go` 1–77 protects a bounded local health score with a mutex and lengthens timeouts as local health degrades. Slow observation can affect failure decisions, so node silence alone is not proof of maliciousness or dead execution. Complete `alive_delegate.go` 1–18 is an application membership-filter interface, not its implementation.

Partial `state.go` 950–1010 checks protocol details, invokes the configured Alive delegate and rejects on error before adding a new peer; it notes that only a merge delegate is insufficient for passive merging. Partial 1140–1255 holds the node lock for suspicion updates, ignores unknown/old states, refutes self-suspicion, enters suspect state and schedules a timer whose callback rechecks state/change time before calling deadNode. Authentication/transport, configured filters, node-name trust, full dead/alive transitions and partition behavior remain unread. This legitimate peer substrate does not grant workload permission or guarantee unique job ownership. No network cluster was started.

Admission/protection continuation: complete `config.go` 1–398, `config_test.go` 1–96, `keyring.go` 1–173, and `security.go` 1–222 now read. Config separates labels/bind/advertise/probe/suspicion controls (19–166), encryption verification/keyring and delegates (168–212), CIDR controls (252–255), parsing (271–294), and defaults/helper predicates (302–397). VerifyIncoming/Outgoing default true, but the default keyring/key are nil; EncryptionEnabled requires a nonempty keyring. **A true verification toggle alone is not proof encryption is active.** Partial UDP ingest in `net.go` 370–445 checks label and conditionally decrypts, rejects failed decryption when verification is required, then dispatches the resulting payload. Partial stream read 1174–1235 rejects plaintext when encryption is enabled and required. Initialization, transport reachability and full dispatch remain unreviewed.

`security.go` uses AES-GCM with random nonces and label associated data, validates version/length, tries installed keys and authenticates before returning plaintext. This is source interpretation of use of standard crypto APIs, not cryptographic implementation certification or a replay-protection proof. `keyring.go` validates key sizes, controls primary selection and installed decrypt keys, and serializes operations with a mutex. Shared-key possession is a group trust boundary, not individual account attribution or per-job permission; a departing member's workload credentials and group access need separate revocation considerations. No key was generated or installed in a real cluster.

Specific source/comment disagreement to retain: config.go 252–255 says an empty CIDR list blocks connections, but IPMustBeChecked at 359–362 tests `len > 0`, and IPAllowed at 365–368 returns nil when that predicate is false. Thus **at this helper boundary**, both nil and an empty list skip filtering. Complete config_test.go covers nil defaults and several nonempty allowlists, without an explicit empty-list denial case. This is a narrow source-established discrepancy, not a demonstrated remote exploit or a claim about every outer transport. Do not rely on the comment to construct a deny-all policy. No Go runtime test was performed.
